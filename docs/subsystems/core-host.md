# core-host

The server side of the patched `ds-bot` core (`core/`): the part of [ds-bot-core](ds-bot-core.md) that runs in DSH. Split out of that page so a change to the browser client or to the pin and patch tooling does not have to edit this one. Pin, patch format, `core/dev/` and the invariants about `ds-bot/` and `client.js` stay on [ds-bot-core](ds-bot-core.md).

## Owns

- Core server: roster/store, tools, turns/delivery, groups, conversation parts, search index, images, browser bridge, `api/bot` channel.
- `core/index.js` — plugin server entry; `core/src/host/` — host modules (roster/store, tools, turns/delivery, groups, channel, remote chats); `core/src/shared/` — code both sides import.
- `core/web-search.js` — standalone `auto` web-search provider.
- `core/test/identity.test.js` — the state identity schema tests (store `state.json` v2, #47).
- `core/test/room-membership.test.js` — typed room participants, authorship and the membership-window history rule (#50).
- `core/test/remote-room.test.js` — granted remote participants, per-viewer presentation and ungranted-Bot refusal; #90 room rules (a room with friends' Bots takes granted local Bots only, revoke evicts, fanout checks author and recipient, room-code Bots); a friend's chat `pendingCount` from `listChatApprovals`. The refusal of an ungranted local Bot next to a friend's Bot (names, `details`, the same group made once the Bot is shared, an ungranted Bot's lines never fanned out, `details` through the channel); `core/test/new-chat.test.js` covers `ungrantedLocalFix` and the new-chat card.
- `core/test/reach-policy.test.js` — #90 reach policy: per-Bot grants (default deny, Chief included), the allow/deny matrix per direction, no bypass, hold release and flagged deliveries re-checked, setGrants and `bot.grants`.

## Does not own

- The browser client, `core/client.js` → [core-client](core-client.md).
- Pin, patches, `core/dev/`, `core/types/` → [ds-bot-core](ds-bot-core.md).
- FlyBot plugin API surface (`core/src/host/hooks.js`) → [plugin-runtime](plugin-runtime.md).
- `plugins/tree/`, `plugins/social/` → their own pages.

### A workflow is data (#1272)

A workflow definition — node ids, the role on each node, the typed artifacts each one takes in and
hands out, the edges and any declared loop — is read from the file and from nothing else:
`core/src/shared/workflow.js` special-cases no node id, and `core/src/shared/artifact.js` names no
producer. A five-node content workflow, the `blank` preset and the `repo-dev` preset pass through
the same validation, the same column order, the same layout and the same input check.

A node refuses to start on an input that is missing **or stale**, and the sentence names the
revision the node read and the one the source holds now; the engine never decides a fact, and a fact
it could not read refuses instead of passing. Validation and refusal live in the pure half, so a
flowchart can be asserted against a definition with no browser, no network and no clock.

Two rules keep that from drifting:

- **One word for one thing.** A node names a `role`; there is no second spelling for it, and no
  definition can state both and disagree. A guard's `is` is likewise kept as written — an unknown
  check refuses with its own sentence instead of being read as `present`, because a guard that can
  never refuse is worse than a guard that is missing: it looks like a check. A fact is keyed by its
  parsed spec, so `text: draft` and `text:draft` are one fact (`canonicalSpec`), in the producers,
  in the consumers and in the declared input and deliverable lists alike — and in `enterNode` /
  `inputStates` too, so a definition that spells an input `text: draft` reads the `text:draft`
  artifact it has instead of refusing a fact that is there (#1298).
- **The board's columns are the definition's, and a node may draw none.** `workflowColumns` returns
  the nodes in dependency order with the `column` each card sits in (`not-started`,
  `in-progress`, `done`); a node carrying `column: false` stays in the definition and out of the
  board, which is how `review` is a pull request's state rather than a third lane (#1265), and a
  definition that states no column keeps the node id, so nothing that already read these columns
  moves.

Refusal sentences are not re-typed per surface. The three the merge gate emits for a held pull
request, a moved head and a conclusion that is not a PASS are written once in
[`.github/scripts/fixtures/workflow-cases.json`](../../.github/scripts/fixtures/workflow-cases.json);
`merge-gate.mjs`'s `judge` (which `enqueue-guard.mjs` calls, and whose joined reasons it prints) and
the `repo-dev` preset's gate guards are both asserted against it, byte for byte, and neither file
imports the other (#1272 acceptance 9). The facts those guards read come from
`core/src/host/workflow-facts.js`, one function per fact, where a fact nobody could read is
`unreadable` and never a guess (acceptance 10) — a check run that ran but reported no conclusion
included, since "still running" is not a reading (#1298).

**Step 3 is the surface** (#1299). A definition is a file — `workflows/<id>.json` in the workspace —
that the host reads and writes (`workflows`, `workflow-save`) and the page edits; the two presets are
copied by *Customize* and never written, and `workflowBytes` is canonical, so saving an unedited
definition produces identical bytes. The per-Bot task board does not draw a column per workflow node (#1363). A definition still
names `column` on each node, and the running layer opens a task card for a node that may start.
That card sits on the task board by its task status (Not started / In progress / Done).

**Step 4 is the running layer** (#1316). `workflow-run.js` is the one place a job becomes node cards,
and it decides nothing: `enterNode` says whether a node may open on the facts just read, and a
refusal is that sentence unchanged — the runtime writes none about a node's inputs. A card is queued
for `node.role` and created unassigned, so the hand-off is the queue's own claim (#1247) and no second
dispatch path exists; the cards a job already has are the record that a node opened, so a replayed
tick, a restarted host or a re-read of the same facts opens nothing twice. Opening the next node is a
fact and not a follow-up action: node *n+1* opens when its inputs are present **and current**, and a
stale one refuses with both revisions. A held job opens nothing on any node and is refused in the
definition's own sentence — the `no-hold` guard, rendered with the fact it expects (`pr: hold`), which
is the merge gate's wording and not a second copy of it; a definition that guards no held pull request
gets the holder's name and no sentence, because this layer writes none. A hold names its holder or it is no hold at all (#1337): a blank string — the shape “the pull-request query answered nothing” arrives in — and a hold no name can be read from plan exactly like no hold, so a job is never refused whole with no sentence to show, while a named holder still refuses every card-less node in the definition's own sentence. A job is done when its terminal
node's outputs are current, never because a card was moved or a merge was claimed. Hanging that card under a GitHub issue was the delivery board (#1265) and is not
built (#1363). The planner still answers which node cards may open.

### Default harness and usage ledger (#903)

Step 0 of #874 Option B is behavior-neutral: one declarative harness and five usage fields that every `calls` row must carry.

- `src/host/harness.js` installs as `rt.harness` / `rt.resolveHarness` / `rt.routeHarness` after `store` in `MODULES` (`core/index.js`). `rt.harness` is always the `default` harness: it names the existing prompt / tools / model / step·retry modules and notes that verifiers live in CI / merge-gate / `core/dev/eval`, not as an in-process Step 0 list. Unknown harness ids throw. Magpie stays out of scope; nothing under `core/dev/harness/` is edited here.
- Tree exception: `@flybot/tree` keeps its own marked prompt under `plugins/tree` (not one of `ds-bot/` · `patches/ds-bot/` · `core/`). Every harness lists that exception; injection stays outside the harness file so eval `P3-tree-split` still passes.
- Usage ledger `calls` is version 3 (`LEDGER_VERSION`): columns include `harness`, `issue_pr`, `tool_calls`, `wall_ms` beside the existing token fields. `withUsageFields` fills defaults (`harness` → `default`, the rest empty/0); `missingUsageFields` fails a row that lacks any of the five. `foldCalls` counts `tool/call` events, computes `wallMs` from the attempt start, and takes `issuePr` from turn text (`extractIssuePr`) or from `rt.noteUsageIssuePr` when a caller tags the session. Rows without those turn signals stay `''` / `0` by design, not as a silent shell that never wires turn data. `foldCalls` also copies `from.harness` onto the row when a caller passes a known id, and leaves `state` as `{ provider, model, retry }`.
- Fixture for acceptance: `core/test/fixtures/usage-sample.sqlite` holds one real `calls` row. Covered by `core/test/harness.test.js` and `core/test/usage-fields.test.js`.

### Harness tiers (#874 Step 1)

Lite, Medium, and Heavy are three configs on the Step 0 harness, not a second runtime.

- `resolveHarness('lite' | 'medium' | 'heavy')` returns the same module pointers as `default` plus a declared budget: `prompt.maxChars`, `tools.maxCalls` and `tools.allow` (`null` on Heavy means the full set the host registers), `model.maxTokens`, `stepRetry.maxSteps` and `stepRetry.maxRetries`. The numbers rise from Lite to Heavy. `applied` is false: prompt, tools, model, and turn code keep running as they do for `default`.
- Triage selects a tier with exactly one label: `harness:lite`, `harness:medium`, `harness:heavy` (catalogued in `.github/labels.json`; a maintainer creates them with `sync-labels.mjs --apply`). No such label, or any other label including `risk:T*`, routes to `default`. Two tier labels, or an unknown `harness:*` label, throw. The controller does not write these labels.
- `harnessPro(config)` is the offline check an RSI edit of a tier has to pass: the config still names `./prompt.js`, `./tools.js`, `./models.js`, and `./turns.js`, its `verifiers.offline` list is `ci`, `core/dev/eval`, `rsi-baseline`, and it carries no key or token field. The function does not run those three checks and does not call a model. Running them is the pull request's own CI, `node core/dev/eval/run.mjs --list`, and `node --test .github/scripts/rsi-baseline.test.mjs`.
- `rt.noteUsageHarness(sessionId, idOrLabels)` stores the chosen tier for that Session. Later `foldCalls` rows and live meter rows record it in `harness`. Clearing it records `default` again. Issue/PR, tool-call count, and wall time stay the Step 0 fields.

### Experience library (#874 Step 2)

Lessons keyed by repository and tech stack, kept off the global `LESSONS.md` bag and off the harness tier objects. This is not Option D: nothing rewrites a tier while a task runs, and the library does not call a model.

- Files live in `core/dev/experience/repos/<owner>/<name>/<id>.json` and `core/dev/experience/stacks/<techStack>/<id>.json`. A repo file names that `owner/name`. A shared stack file has `repo: null` and lives only under `stacks/`. A repo file may list `techStacks`; those tags do not publish it to other repos. The shape is trigger, wrong, right, plus a date, the same spirit as `LESSONS.md`, scoped to the key.

A tech-stack lookup returns `repo: null` entries from that stack. Passing both returns the repo's tagged entries plus the shared stack entries. `query` filters `id`, `trigger`, `wrong`, and `right` after that scope is fixed. Sort is date descending, then id ascending.
- `harnessExperience` / `rt.harnessExperience` call that reader. `resolveHarness` still returns the Step 0 / Step 1 config. `applied` stays false. Budgets stay as declared in Step 1. `harnessPro` still names CI, `core/dev/eval`, and `rsi-baseline`. The library does not replace those checks.
- A new lesson is a JSON file in git. `node core/dev/experience/check.mjs` checks the tree (path and fields must agree). `add` writes one new file under that tree and refuses to overwrite. It does not edit harness configs. `core/dev/` is outside the npm `files` list, so a packaged install's default read returns no entries instead of failing the host. Covered by `core/test/experience.test.js`.

### Room execution boundary

`groups.js` owns room scheduling, membership checks, private-brief selection,
prompts, seen cursors and reply presentation. DSH session opening, member turns,
running snapshots and cancellation go through `room-participant.js` (#216).
Existing `room.sessions` / `groupOwners` links and host permission paths remain
unchanged. The driver releases completed waiter timers/listeners and follows
context rollover for execution events. This internal DSH boundary adds no
external backend or task-specific session mapping; see the
[same-room participant contract](../interop/room-participants.md) for those gaps.

A member whose Bot record carries `external` is spoken for by a supervised subprocess instead of a DSH Session (#198). `room-participant.js` `createRoomParticipants` is the one boundary: it keeps the DSH driver for every other member and routes a member with that record — and later that member's own session id — to `room-participant-external.js`. The record is a typed block, `external: { driver: 'subprocess', command: [argv...], cwd?, env? }`, written through `roster.js` `cleanExternal`, which refuses a string command (a shared room setting that runs a shell line is an injection surface), any driver but `subprocess`, and an interpreter as `command[0]` (`sh`, `bash`, `pwsh`, `env` and the like): an argv array whose first word is a shell is the same shell line spelled differently. One process is supervised per (room, Bot) and talks one JSON object per line on stdio (`{ type: 'turn', text, note, from, exchangeId }` in, `{ text }` or `{ error }` out), so the same external Bot can be invited to a second room as a second process over one identity. `open`, `runTurn`, `snapshot` and `cancel` reach each driver through the router. Start, clean exit, crash, a user stop and the room-turn timeout are explicit states: a crash is reported as the Bot's own line in the room (`groups.js` `externalRoomLine`), and a turn that reaches a dead process ends as `{ failure }` instead of silence. A process that died is not a dead end: the next turn in that room starts a fresh one, which is what the room's line promises. A stop asks on the protocol first (`{ type: 'stop' }`), sends `SIGTERM` after a short grace and `SIGKILL` after a longer one, so a child that ignores the request and the signal does not outlive its seat; an entry whose stop is still in flight is never reused for the next turn, and a turn the user stopped ends as nothing to answer rather than a failure. A crash line carries the last ~200 characters of the child's `stderr`, flattened to one line, so `exit 1` is diagnosable from the room itself; a timeout reads as `timed out`. The seat owns the process: `store.js` `dropGroupSession` closes the `(room, Bot)` process when a member is removed or the Bot is deleted, and `groups.js` `install` closes the rest on host teardown (`ctx.effect`).

### Group standing section (#894)

A member's group Session reads the group's fixed rules from a system-prompt section, `bot-room` (order 10150, after DSH's own sections so the member's group Session and its own chat share the longest system-prompt prefix), not from each turn's message. `groups.js` `standingText` renders it from room settings only: the members line (or the face roster), `@Name` calls, the notice, the admin note or the face lead / member note, the face rule for lines that name no Bot (`routeRules`: the member's default, the exception for a line to everyone, other homes' Bots answering in their own home, never explain a pass), and `ROOM_REPLY`. DSH renders sections on every model step and re-projects them after a checkpoint or in a new part, so the rules are always in front of the model while the history keeps one copy per change instead of one per turn. The own chat and the group's relay Session render no section (`''`). Each turn's message keeps the round (earlier lines, this round, references, who is still working, speaking order, position), a short `routeNote` (this line: to everyone, the lead's or "Default to [PASS]", who spoke last, who already answered), and `ROOM_REPLY_NOW` (or `ROOM_REPLY_FORCED`). `room.noticeSeen[botId]` keeps a 16-hex SHA-256 mark of the notice a member last saw, so its next turn says only that the notice changed or was cleared. DSH runtime context (`systemPrompt.context`) is not used: its `runtime-context` user messages are not a no-request kind in `turn-origin.js`. Covered by `core/test/rounds.test.js` and `core/test/context-sharing.test.js`.

### Room context budget (#1203)

A group turn does not hand the model the raw ring buffer. `src/host/room-context.js` `fitRoomLines` takes the lines the count caps already chose (`ROOM_FIRST_LOOK` 12, `ROOM_DELTA_MAX` 24, and `ROOM_EARLIER_MAX` 8 of those from before the round) and keeps a newer-first slice of at most `ROOM_CONTEXT_BUDGET` characters (4000). The budget is characters because the measured essays are mostly CJK, about one token per character. A long bot line that reads as CI, merge-queue, or review narration (`statusShaped`: at least 400 characters and two of the status hints) is collapsed to a one-line stub that keeps the opening and up to four `@` names. Since #1251 every writer of `room.log` stores that same stub rather than only the turn: `groups.js` `appendRoom` (a group round) and `room-membership.js` `append` (`postRoomMessage`, a seat's `line` op, a face-room event) both pass the stamped line through `prepareRoomLine`, so the stored line and the next turn cannot disagree. A person's line (`botId` absent), a `kind`-carrying event line **from this home** and a short handoff come back unchanged and are stored verbatim. A fenced peer line (#98) is compacted *inside* its fence and wrapped again with the same `from` name, because compacting the fenced string would strip the markers and store a guest's text as this home's own; the fence decides *before* the `kind`/`botId` exemptions, because both travel from the other home (`room-membership.js` copies the peer's `kind`), so a peer could otherwise mark its essay `notice` or type it as a person and store it whole. A long Bot line that is not status-shaped is still stored whole — the store gate reuses `#1204`'s rule, it does not widen it. When lines are left out, the turn says so and points at `read_group_chat` for an exact earlier line; `read_group_chat` returns the stored line, which for a Bot essay is the stub. Covered by `core/test/group-work.test.js`, `core/test/room-membership.test.js` and `core/test/remote-room.test.js` (the stores) and `core/test/room-context.test.js` (the rule).

The open task board for that room is a compact snapshot in the same turn (`formatRoomBoard`): the newest overall task, then its subtasks and any room card that is not under a different overall task, up to eight cards. Done cards stay off. Titles and notes are one line, capped, with `<` and `>` removed. An unclaimed queue item reads `unassigned [open 3h Dev]` — its role and its wait on the card itself — and the snapshot ends with one line per role that has something waiting (`- Queue Dev: 2 waiting, oldest 3h`), so starvation is visible without reading every card (#1247). A role with nothing waiting is omitted. A face-to-face room has no snapshot and keeps `@Name` as how its lead gives a part. The standing section does not carry the snapshot or the transcript, so it still changes only when the group settings change. In a group that has a board, `ROOM_REPLY_BOARD` and the task-lead note say assigning, claiming, and progress are `track_tasks` writes (overall task, subtask, assignee, column, progress), `@Name` only wakes, and a status the board already shows is `[PASS]`. A task-drive wake in the group says to set that card's column and progress, and appends the same snapshot after its cue. Covered by `core/test/room-context.test.js`, `core/test/rounds.test.js`, and `core/test/task-drive.test.js`.

### Who is working (#1213)

The board says what is open; the turn also says which member holds it, because a member that claims a card and stays quiet used to be indistinguishable from an idle one. `room-context.js` `formatRoomPresence(tasks, { roomId, members, now })` reads the same `rt.state.tasks` at the moment the turn is built — no write, no message, no heartbeat — and `groups.js` `roomPrompt` renders it just before `formatRoomBoard`, for a room with a board only (a face-to-face room gets neither). One line per member that holds an unfinished card in that room: `- Dev2 — #1081 <title> (in progress 15%, open 27 min)`, the number from the card's `target`, the column word from `columnOf`, progress from `progressOf`, age from `createdAt` (`open N min`), and `, moved N min ago` when `updatedAt` is at least a minute newer; a card waiting on an input reads `waiting on an answer`, a 0% card `just claimed`, and a second card on the same owner is `+N more`. Every member that holds no card gets `- <Name> — idle (no open card)`, so "nobody is working" is readable too; when no member holds a card the block is the single line `Who is working: nobody (no open card).` At most eight member lines and `ROOM_PRESENCE_BUDGET` (400) characters, then `- +N more member(s)`; titles are flattened and cut, and a card's note prose never rides along. Only card state is rendered — never CI, the queue or a verdict, which #1203 keeps out of the chat. Covered by `core/test/room-context.test.js` and `core/test/rounds.test.js`.


### Group loop guards (#557)

`post_to_group` has no cap on the rounds Bots start in one group between the user's lines. The old `ROOM_BOT_ROUNDS` (3) gate was turned off by owner decision 2026-10-21 07:34 Asia/Shanghai: it refused a recurring scheduled task's fourth post with a tool result only, so owner-set runs stopped overnight with nothing shown in the group. A saved room may still carry `botRounds`; nothing reads it, and `channel.js` keeps it out of the roster. The guards that stay: `MAX_HOPS` (6) ends a Bot-to-Bot chain (`message_bot`, and `post_to_group` from a relayed turn); `MAX_UNREAD_REQUESTS` (10) per Bot chat; `ROOM_TURNS_EACH` / `ROOM_ADMIN_TURNS_EACH` (2 / 4) per member per round, except the room's admin when a member names it with `@`: that call is never dropped by the cap (#804), because it is a report to the coordinator rather than a chain, and the round's own turn limit still bounds the round; `ROOM_LATE_ROUNDS` (10) late replies answered before the user speaks again; and a Bot cannot `post_to_group` into the room it is speaking in. Face-to-face rooms take the same path. Covered by `core/test/rounds.test.js`.

### A line sent while a member speaks (#1267)

A person's line sent into a group while a member is speaking now reaches that member inside its turn, instead of waiting behind the speaker. `groups.js` `runRound` starts `watchSpeakerLines` around the member's `runTurn`: every `ROOM_MID_LINE_POLL_MS` (100ms) it reads the same Session queue the round drains at its loop head (`waitingLines`: queued or steered `user` lines) and hands each new one to `speakMidLine`. That appends the line to the room log at once, puts it in the running round's replies, marks it with `notePostedLine` and drops the relay's pending copy, so the next relay neither logs nor answers it again. The member gets it through `rt.deliver` with `steer: true` and the note `ROOM_MID_LINE` (`[Group chat "..." · the user sent this while you were speaking; answer it now]`), so its next model step sees that the line arrived after it started and never answers it as if it had been there from the start. The one exception is a line that only says stop (`ROOM_STOP`: 停 / 停下 / 停止 / 别做了 / 不要做了 / stop / stop it): the speaking slot is marked `superseded` (`slotLabel`: `(stopped by the user)`), `participant.cancel` cancels that turn, a `stopped` reply replaces its answer, and nothing the stopped turn said is posted. That line stays in the Session queue, and the round's next head drain opens it as a fresh line for the room to answer, admin first; `round.midLineIds` keeps the drain from showing it in the replies a second time. Covered by `core/test/rounds.test.js`.

### A group round's closing report (#913)

When a Bot posts with `report_back`, `reportRound` sends it the round's closing report. A member the round's line named and that ended its turn without a line (a pass, or no reply at all) was addressed and did not answer, which is not the same thing as a member that read the line and had nothing to add: the first gets `No answer to your @: <names>.` (the poster's own line or a person's line named it; another member's call is `Called, but no answer: <names>.`), and only the rest stays under `Stayed silent:`. A slot keeps `addressed: true` when a person's line named it, and `by: <bot id>` when a Bot's post did, so the report reads the slots instead of `round.passed` alone. Nothing is re-called: the everyone-passed fallback (`fallbackDue`) keeps its single extra turn, and the member prompt is unchanged. Covered by `core/test/rounds.test.js`.

### An `@Name` in a Bot's own line calls that member (#932)

A member's own line calls the members it names in two shapes where the call used to be lost. While a round runs, `post_to_group` used to be shown in the round and re-delivered to the Session after it, so the names in it were called only by whatever round that re-delivery opened — that is, after the round's report had already listed them as silent. `showInRound` now reads the line's `@` names (the members of the room, never the sender) and keeps them as `round.calls`; `runRound` drains them at its loop head (`drainMidCalls`) with the same `ROOM_TURNS_EACH` / `ROOM_ADMIN_TURNS_EACH` bound and the same round limit as a call made from a reply, so the call lands inside the running round and never bypasses the cap. The held post carries `called: true` (queued by `turns.js` into `roomInbox`) and `openingSpeakers` opens no round for it, so a named member is called exactly once. Second shape: a late line past `ROOM_LATE_ROUNDS` is quiet, and `openingSpeakers` read `quiet` before its `@` — an explicit name was swallowed and the admin answered a line that named someone else. The mentions are now resolved first: `quiet` caps only the spread of a line nobody was named in (it returns nobody then), while a name written in the line is called. An event post (a member's failure, stop or resume notice) still calls nobody, and a name outside the room or the sender itself is not a call. Covered by `core/test/rounds.test.js`.

### A dispatch is a board assign (#1254)

An admin's `@` used to be the room's control plane: every `@Dev #1234 rebase and push` opened a group round for that member, so dispatch stayed chat and the board only recorded what chat had already said. Now the line is the assignment. `work-dispatch.js` `workDispatch(text, { callees })` answers only the shape — exactly one named member, an issue/PR id (`#1234` or a `github.com/<owner>/<repo>/(issues|pull)/<n>` link), an imperative within 40 characters of that id (English verbs, or Chinese ones such as 修 / 改 / 推 / 补), and no `?` — and `groups.js` `dispatchOf` adds the room's rules: a Bot's own post, no `@all`, not quiet or an event, a room with a board, and the poster is `rt.taskLeadOf(room)` (the picked lead, else the admin). `rt.assignFromDispatch` in `tasks.js` then updates the open card that member already holds for that issue (`cardNamesIssue` in `src/shared/issue-ref.js`, re-exported from `work-dispatch.js`: matched on `title` or `target`; a card whose own fields name no issue is matched on its `note`, so a note that merely mentions another issue no longer reclaims it — #1331) or opens one owned by it, still `open` — the host assigns, and the member claims on its own turn, where #1253's claim line is posted in its own voice. The save runs the drive, so the member is woken in its own chat (#1205). A card that is not driving — `result-ready` or `blocked` — is restarted through an edge the state machine already has (`result-ready → working`, `blocked → working`), because `task-drive` wakes only `open`/`claimed`/`working` and rewriting the note alone would leave the member unwoken; a card blocked on an input is reused rather than duplicated, so one issue stays one card, and a stored card with no `actors` list has one started instead of throwing after the note moved. The relay's `speakers` is empty for that opener and the round records no part or pass; the same dispatch posted while a round runs is written from `showInRound` and adds no `round.calls`, so the member is not called twice — but a card write that answers `undefined` is never a silent drop: the opener's `speakers` fall back to the ordinary ones and a mid-round dispatch falls back to `round.calls`, so the member is called in the round instead of not at all. A question, a remark with no imperative, two named members, `@all`, a poster that does not divide the board, and a face-to-face room (no board) keep the group turn they had. The line is still in the room log, and the card shows on the board. Tests: `core/test/work-dispatch.test.js`.

### Team state and access

Sign-in surface only — still not team mode; details in [team](team.md). On top of it, owner-scoped access (#49) adds host module `src/host/authz.js`, installed after member-auth: when any `authSessions` exist, the channel `authorize()` default-denies cross-owner Bot/room/session access, blocks shared non-isolatable resources (secrets, connectors, folder picks, browser bridge, update-install, diagnostics, set-prefs, `add-agent` — the DSH Agent is one per deployment and carries no owner) with `bot/blocked-shared` when more than one member exists, stamps `create-bot` with `actor.memberId`, and filters `view()`/`live()` to the actor; with no sessions the single-human behavior is unchanged. On top of it, room membership (#50) adds host module `src/host/room-membership.js`, installed after groups: a room may carry typed `participants` (`human` / local `bot` / granted remote `bot` with `handle` + owner fields, roles `admin` / `member`, `joinedSeq` / `leftSeq`); log lines carry `authorId` + `authorKind`; history is the membership window (current members and the owner of an invited Bot see `seq >=` their interval; leave withdraws access; rejoin starts a new interval); local cross-owner rooms accept each side's *granted* Bots (#90: default deny, Chief included); a friend's Bot from `social/remote-bots` (`cleanRemote`) may be added and ungranted Bots stay private, and a room with a friend's Bot holds only granted local Bots (a Bot that joined by room code, `viaCode`, only for that room); `view()` labels remotes with an owner badge and shows an invited owner **Shared room from \<inviter\>**. Face-to-face rooms (#83) reuse the same `participants` / membership-window / owner-badge presentation with `origin: 'face-to-face'`: room-only remotes may sit in the room without a person-grant or a friendship, `presentRoom` treats the viewer as a member (not Shared room from), leave skips the two-Bot floor, and `fanoutRoomLine` goes to `rt.faceRoomFanout` instead of friend `flybotSend`. Still not team mode — see [team](team.md). Per-Bot grants (#90) add host module `src/host/reach.js`, installed after room-membership: `state.grants[botId]` is the list of independent grants (one Bot → one grantee, optionally room-scoped); default deny, Chief included; a Bot whose owner is not a member has none. Grants are set with `rt.setGrants`, exposed as `BotView.granted`, `flybot.bot.hasGrant` / `hasAnyGrant`, `flybot.grants` and the `bot.grants` event. `reach()` is the owner policy: a friend's Bot may reach only local Bots granted to that sender, only a granted Bot (or one code-joined in that room) may message a friend's Bot, another owner's Bot is reached only if both sides have matching grants or both are members of the room the message belongs to. It is not a middleware: hooks.js runs it before the `bot.send` chain, again on approval release, and on every deliver with a sender or remote origin (resumed, retried, deferred, re-sent), so no verdict or `bypass` can skip it and a queued message is judged by what is true when it is delivered. Revoking a grant, or replacing its Chief, removes it from rooms that have friends' Bots or several owners at once (`rt.evictUnshared`). Approval binding (#52) completes the held-send half of this: `state.flybot.approvals` records carry `requestId`, a sha256 `version` over the request content, server-derived `ownerId` and `origin` (`via`/`hop`/audience) — claims in the message (`meta`, text) never confer authority. `flybot/decide` is allowed through authz for any signed-in actor and the per-record check happens in hooks (`decide` requires the sender Bot's owner's session, `bot/forbidden` otherwise, `bot/unauthorized` without a session); `release()` revalidates before dispatch and marks the record `stale` when the request changed, the sender or target Bot is gone (also invalidated eagerly on `deleteBot`), or the Bot changed owners; a demoted Chief's sender-side holds are invalidated eagerly on `setMain` (not inside `staleReason`), and `release()` re-checks immediately before dispatch so an in-flight approve cannot go out after a concurrent invalidation. Unknown `invalidateFor` field values throw. `flybot/approvals` lists only the actor's own holds while enforcement is on; decided stale records keep their attribution in state but appear in no member's list. Which statuses still wait for that decision is one rule in `src/shared/approval-waiting.js` (#754): `decide()`, `heldOf()` in the chat view, the in-flight filter that invalidates holds, `PENDING_MAX` and the `APPROVALS_KEPT` cleanup all ask `isApprovalWaiting()`, and `channel.js` counts a row's waiting replies with it, so a `pending_approval` hold (Bot Social's own spelling) is decidable, drawn as waiting and never dropped mid-wait.

- One writer per home (`src/host/home-lock.js`): the first dsh to load `~/.dsh` takes `state.lock` (pid, host, a random token in the file, its mtime bumped on a timer) and a second window on the same data only reads, answering `bot/read-only` and naming the other host. Takeover is **on the next write**, not on a poll (#1027): a window that was read-only claims the free lock inside `save()` too, and a change made outside a request (a plugin, a scheduled task, a delivery) belongs in `rt.mutate(fn)`, which takes over and adopts what the other host left *before* the change is made and written. The writers that changed `rt.state` inline and then called `save()` are gone (#1048): `delivery.js` (a friend's first line and its unread mark, a team exchange) and `agents.js` (add, adopt, archive and remove of the DSH Agent) take the free lock and adopt first, re-resolving their records inside the change, so a write from a window that was read-only keeps what the other host left instead of replacing it with its older copy. `save()` itself never adopts: `adopt()` replaces `rt.state` whole, so adopting there would discard a change the caller has already made (`#1032`). Either takeover prints one line — `the other dsh has closed; this one now saves the Bot team (was pid <pid> on <host>)` — from `refresh()` and from `save()` alike, so a window that writes over the file another host left leaves a trace (#1041). A lock file still naming a live holder on this host (its pid answers) keeps the window read-only, which is the #14 rule. A write that fails does not decide the delivery (#1096): the friend-line mark and the exchange record both land before the agent has the line, so a rejected `mutate()` (the lock was taken away, or the disk refused) prints one warning naming what was not recorded and the line is still handed over — a throw there would drop a message that exists nowhere else. The write chain is also readable: `rt.savesQueued()` is a monotonic watermark — every save this host has accepted since it started, never decremented — and `rt.savesSettled()` resolves once the chain is empty, so a caller that must read `state.json` after a save it did not await — a rollback's own write, in the tests — waits on the store instead of on a delay, where a wait long enough on an idle machine reads a half-written team on a busy one (#1368).

- `list_bots` (`src/host/tools.js`) tags a Bot with `N to approve` while one of its outbound sends is held for the owner's decision (#587): a count of that Bot's pending held sends (`state.flybot.approvals`), never the held message's text, so a coordinator reading the roster sees who is blocked and the tag clears once the owner decides. Covered by the roster case in `core/test/flybot.test.js`.
- The Main Bot list is deployment-wide (#613): `set-main` requires the actor to own `body.id` and, when `body.replace` names the Main Bot whose place the target takes, that Bot too, so a member cannot swap another owner's Main Bot for their own or demote it (both are `bot/forbidden`); `roster.setMain` keeps the same invariant for every caller, refusing a `replace` across owners and leaving `state.mainBotIds` unchanged. A swap inside one owner's team, the plain promotion of a Bot the caller owns, and the deployment-wide list itself are unchanged.
- **A Main Bot retires a Bot; it never deletes one (#638).** `archive_bot` (`tools.js`, Main Bot only) calls `roster.archiveBot`: it writes `fields['flybot-tree'].retired = true` through `rt.setBotField` — the same path and `change` event a plugin's `fields.set` uses, so the tree and the sidebar refresh — and sets `bot.hidden = true`, the flag the tree's own archive uses to keep a Bot out of the default list while Search still finds it (#452). The record, its chat, parts and memory stay where they are, so its history stays readable; retirement has no un-retire path, and the restore entries in the sidebar and the palette only clear `hidden` (`core/src/client/new-chat.js:104`, `core/src/client/palette.js:60`), which opens the chat again but leaves the record retired. The tree's `forestOf` skips a retired record, so its slot under `maxChildren` is free again and adoption leaves it alone. A Main Bot, the caller itself and an unknown name are refused, nothing reparents, and `list_bots` leaves a retired Bot out (the record is still found by name). Retirement is terminal (#1700): the tools that resolve a Bot through `findTeamBot` — `message_bot`, `stop_bot`, `update_bot`, `create_group`, `update_group` (`add_members`, `admin`, `task_lead`) and `archive_bot` — refuse a retired record exactly as they refuse an unknown name, so `message_bot` sends nothing and starts no turn, and `archive_bot` aimed at an already-retired name answers the same "No Bot named …" line. Other host paths that resolve a Bot by name — task assignee, group `@Name`, capability attach, memory scope — are outside this change and tracked in [#1709](https://github.com/ThinkFlowLab/FlyBot/issues/1709). Deleting remains the UI's `delete-bot` call (`roster.deleteBot`), which archives the Bot's memory first. Covered by `core/test/archive-bot.test.js`.
- A deleted Bot's Sessions keep their owner (#1453): `state.retiredSessions` maps a Session id to the Bot id that owned it, written by `roster.deleteBot` for the own chat and its parts and for each group Session and its parts before the Bot leaves the state, so `indexSessions` can put them in `pastOwners` again on the next rebuild. The record only fills what the live indexes do not claim — a live Bot or room holding the same id wins — and it only grows, one entry per Session of each Bot ever deleted, with no pruning in this change. `selfOf` then names a Bot that no longer exists, so `connector-access.js` `whoseAgent` answers `{ unknown: true }` and every connector is refused with `the Bot this Agent works for could not be determined`, in the process that deleted the Bot and after a reload, because the team file carries the record. The owner's own Session, an id no Bot ever had and a call with no Agent keep the connectors. The schedule tools are not covered by this change: they carry no connector id and are refused or allowed before that branch, and widening them is the #1237 decision.

- Context sharing (#53) is specified in [team](team.md), **Context sharing foundation**: the own-chat brief is share-gated (`share-brief` / `briefShared`), a memory review reads only its owner as the user (`isUserLine`) and labels another human as `peer` (not `bot`), and keeps cross-owner entries out of the team scope (`teamAllowedFrom`), `list_bots` lists only the caller's owner's Bots (a granted child: that child's `createdBy` subtree), Bots granted to the same owner, and Bots in the current room — another owner's folder and instructions stay private — and a `dsh-session:` chip in actor-authored `send` / `room-post` / `answer-question` / `schedule-create` text must resolve for the author (`sessionOwnedBy`; `schedule-create` authz keys off `body.target`). Bot-authored group posts and Bot-to-Bot / own-chat followups drop chips so they cannot tunnel a private chat into another Session. Host modules: `src/host/groups.js`, `src/host/memory.js`, `src/host/tools.js`, `src/host/channel.js`, `src/host/room-membership.js`, `src/host/authz.js`. Team mode stays disabled.

### Memory recall: semantic and graph

- `src/host/memory-search.js` derives two recall aids from the memory files that `src/host/memory.js` already reads; both are pure and rebuildable, and the Markdown files stay the only source of truth.
  - Hybrid ranking: `termsOf`/`buildIndex`/`searchIndex` build a sparse TF-IDF vector per entry over words, word character trigrams (4+ letters, so a shared stem matches across endings) and CJK uni/bi-grams, and rank by cosine. `recall` uses it only when called with `semantic: "true"`; the default exact-word path is unchanged, so an existing call scores and prints exactly as before.
  - Graph: `buildGraph`/`relatedOf` turn `[[topic]]` references into topic→topic edges and a `by:` metadata value into file→Bot edges; `recall` with `related` walks them (undirected, up to two hops) and lists what is near a topic or Bot. ### Decisions a Bot records (#396)

- `src/host/decisions.js` gives a Bot one small tool, `record_decision({ option, choice, why })` (`choice` is `used` or `rejected`), so a "considered and rejected" choice a reviewer cannot otherwise see is written down. The host appends one JSON line per decision to `<home>/decisions.jsonl` (bounded on disk at the newest 2000 lines and 1 MB, trimmed by the host as it appends; a read parses at most 1 MB; one write at a time; a write failure is a warning, never a turn failure) and fires the entry on the activity feed as `decision`. A Bot has no tool to edit or delete a past entry.

### Tasks

The requester may also cancel a `result-ready` task before acceptance (#202).
`task-cancel` keeps the returned summary and actor history; the cancelled task
survives restart and cannot later be accepted, restarted or returned again.
Accepted/failed/cancelled tasks stay terminal. This records the requester's task
disposition, not proof that an external runtime stopped; no runtime abort or
side-effect rollback is implied.

A tracked request with a stable id (`task-<hex>`) and a small state machine, owned by `src/host/tasks.js` with `state.tasks` (additive; corrupt values reset, no version bump). States: `open → claimed → working → blocked ⇄ working → result-ready → accepted`, with `cancelled`/`failed` terminal and `accepted` reachable only from `result-ready` — a failed or cancelled task can never display as accepted (#54). Transitions after create are the requester's (server-derived `requesterId`, the signed-in actor or the single owner; `bot/forbidden` otherwise, `bot/stale` on invalid moves), recorded with per-status actor entries. Create does not require owning the Bot: a matching per-Bot grant, or both the requester and the Bot as current members of the named room, is enough; outgoing holds stay the owner's (#52 card). A working task's held send blocks **that** task (`meta.taskId` stamped on the send, matching origin when the Bot has several working tasks; `updatedAt` is strictly increasing, so two starts in one millisecond still order) with the approval id; the owner's decide resumes (approve) or cancels (reject) it; deleting the responsible Bot fails its open tasks. `result-ready` is protected from prune while it waits for acceptance. Endpoints `tasks` / `task-create` / `task-accept` / `task-start` / `task-return` / `task-accept-result` / `task-cancel` are an explicit authz allow-list and are record-checked in tasks.js. Records store pointers and a copied summary, never private transcripts. Clarification and `workBotId` wait on #55's exchange wiring. Team mode stays disabled. After `task-create`, `task-update` and `track_tasks` save, the host asks `rt.onTaskWrite` (hooks exposes it as `flybot.tasks.onWrite`, [plugin-runtime](plugin-runtime.md)). A returned `ownerBotId` that names a different local Bot is stored and saved once more; that second save does not ask again. A missing, remote or identical id leaves the owner (`core/test/task-route.test.js`, #1318). `track_tasks` routes every card it saved, after its own save and before it answers, so a card a Bot records itself reaches the same listeners as a board write made through the channel API (#1462).

### The typed task contract (#1720)

Five additive fields sit beside the record above; none changes what an existing field means, and a record stored before this slice reads back with them absent and nothing rewritten. `taskClass` is the typed kind (`work | rework | release | triage | meeting`) — it is not `kind`, which keeps its group-card meaning, so a group card is `kind: 'group'` with `taskClass: 'work'`. `reworkOf` names the card a rework card fixes and is not `parentId`, which stays the one-level part-of-overall link (`settleOverall` is untouched); a rework card therefore fires no overall-card settle. `handoff` is `{from, to, at, reason}` with both roles named (a role is known when a Bot carries it, or it is `requester`; an unknown role is refused with the role quoted back), `reason` at most 300 characters. `evidence` is at most eight `{sha, pr, check, at}` pointers, and `lease` is `{holder, takenAt, expiresAt}` on a claimed card. Every value is validated on write by one function, `writeContract` in `src/host/tasks.js`, reached from `track_tasks`, `task-create` and `task-update`; it reads every field before it assigns one, so a refusal (`bot/invalid`, or `bot/unknown-role` for a role no Bot carries) leaves the card exactly as it was. A review rejection (`task-send-back`) records the handover on the original, moves it to `working` and opens exactly one child card with `taskClass: 'rework'` and `reworkOf` naming the original — the single write that returns the original to `result-ready` is the acceptance of that child, guarded by the original still being `working`, so a replay creates no second child and moves the original once. A claim takes a lease (30 minutes); a claim on a live lease is refused as `bot/lease-held` with the holder named, and an expired lease returns a queued card to the queue. The read model does not copy: `project-board.js` puts the five fields on the row it already emits when the card carries them, so a pre-slice card keeps its old row shape. Tests: `core/test/task-contract.test.js`.

### Task input waits

`task-wait-input { id, question }` is a requester-only bookkeeping action on a
working task (#207). It records `blocked`, `waitingFor: 'input'` and a fresh
`inputRequest { id, question, requestedAt }`. `task-answer-input { id, questionId,
answer }` requires that exact current question, the same requester and no pending
task approvals before returning to `working`. Question/answer must be nonblank
strings of at most 2,000 characters. Only the latest selected question/answer
snapshot is kept, with actor entries linking its question ID; chat history is not
copied. The wait and snapshot survive restart.

`task-start` starts a claimed task only. It cannot resume a blocked task; approval
decisions and matching input answers are the respective resume paths. An
approval-only wait cannot be replaced by an input request. Explicitly stamped
`meta.taskId` sends may still link an input-waiting task; untargeted sends do not
guess that association. Such holds accumulate in `inputApprovalIds`, preserving
all outstanding holds while a sibling task stays untouched. Each approval clears
only its own ID; approval does not answer the question. Any rejection cancels the
task. Cancellation/Bot deletion clear active input/approval-wait markers while
retaining the selected input snapshot; late answers cannot revive a terminal task.

These endpoints do not prompt, deliver a clarification, resume an agent or grant
execution/tool permissions. Automatic exchange wiring, runtime-scoped observation
credentials and team mode remain separate work under #55/#198.

### Bot task board (#1058)

Each Bot's work sits on the same `state.tasks` records. A column is read from the status (`open`/`claimed` not started, `working`/`blocked`/`result-ready` in progress, `accepted`/`cancelled`/`failed` done) by `src/shared/task-board.js`. `task-update` sets `priority` (`urgent`/`high`/`normal`/`low`), `progress` (0–100), `note` and a column; a column walks the existing states forward (`open` → `claimed` → `working` → `result-ready` → `accepted`) and refuses a reverse move or a blocked wait. The requester or the Bot's owner may update. Anyone else, including a group admin, may not. The `tasks` read lists active work only; `{ archive: true }` is the same read including the finished rows, and `{ archive: true, limit: N }` returns the newest N finished rows by `updatedAt` (tiebreak `createdAt`) and no active rows — the default read is what carries active work — so the board's poll carries the slice and not the history. A `botId` or `roomId` read filters before that cut, so the page is that Bot's or room's finished rows and not the whole visible scope. A read without `limit` still returns every settled row on purpose: it is the id-lookup and tooling path (`statusOf`, a Bot reading a settled row), not what the board polls (#1252).

`track_tasks` is the conversation path. The calling Bot creates or updates only its own tasks (`source: 'conversation'`, `requesterId` the Bot's owner, `origin.sessionId` the turn, `origin.roomId` the group when the turn is in one). The same title in the same group updates the open task instead of adding another. The prompt tells the Bot to record work the user or a group actually handed it, to continue the unfinished task the tool names next, and to pass `ask` when it cannot continue without an answer.

A group job is one overall task plus a subtask per Bot (#1099). The overall task is `kind: 'group'`, owned by the Bot that records it, and tagged with `origin.roomId`. A group keeps one open overall task; recording another updates that one. A subtask sets `parentId` to that task. One Bot divides the board (#1182): `room.taskLead` when that Bot is still a member, otherwise the group admin. A face-to-face room has no board, so it has no task lead. Another Main Bot does not plan. The user, a Main Bot, or the group's admin sets the lead with `update_group` (`task_lead`, `none` clears it) or `update-room` (`taskLead`); group settings shows **Make task lead** / **Use the admin** on a group that lives here. Assigning a subtask to another member claims it (`open` → `claimed`) so the assignee starts without a confirmation, and wakes that assignee in its own chat (#1205); the assignment does not open a group round. The assignee then sets the column to in-progress with `track_tasks`; a chat line does not assign, claim, or record progress. The group board shows that above the columns. The requester stays that Bot's owner, so the lead still cannot move the card through `task-update`. A member updates the card assigned to it, records its own room task, or links its own subtask to the overall task. Only the lead records the overall task or assigns a subtask to someone else. When every child has ended, the overall card completes through the same transition a person's move uses: `accepted` with `progress` 100 when each child ended accepted or cancelled, `failed` when any child ended failed, so a failed part is never hidden behind a green overall card; an overall card already blocked or waiting on a result is left to its owner (#1252). A child also ends when its Bot is deleted (`failed`) or when the owner rejects the send it was waiting on (`cancelled`); both doors settle the overall card the same way, so the card a person sees is closed rather than left working.

A lead can put work in a pull queue instead of naming an assignee (#1247). `track_tasks { tasks: [{ queue: true, role: 'Dev', priority, title }] }` records one item for that role: `queueRole` names it, `queueBy` is the lead, and `ownerBotId` stays the enqueuer until a claim, so an unclaimed item wakes nobody — `task-drive` skips it. Only the room's lead enqueues, and an item whose role no live member of that room carries is refused (`no-member-with-role`) instead of sitting for ever for a role nobody has. `track_tasks { claim: true }` takes the highest-priority item of the caller's own role, oldest first on a tie (`compareForQueue`, not `compareForWork`, whose tiebreak is newest first), and `id` claims a named item; a member of another role is refused by name (`not-in-role`), never silently. One member holds one card in progress, so a member already holding one gets nothing — a blocked card waits on a person and does not count. The claim is compare-and-set: the item is read again after the pick yields, and only one still open is taken, so two claims leave exactly one owner. `track_tasks { release: { task, reason, retryInSec } }` returns a claimed item (`blocked → open` included) with `retryAt`, and it is not offered again before then. A claim sets `ownerBotId` and `claimedBy` to the member and keeps `queueRole`, so the card the board and room presence read is the same card: claiming is a board write, not a second row. Tests: `core/test/task-queue.test.js`. Reading the list orders unfinished work by priority (urgent, high, normal, low) and prefers an in-progress task when the priority is the same. `ask` walks the task to working and then to the existing input wait (`waitingFor: 'input'`); the reply tells the Bot to call `ask_user` for the user, and to post one short question in the group only when a person there has to decide. `answer` resumes that wait. The question is the same record the inbox already shows for a blocked task.

The claim is public (#1253). When a card in a room moves out of `open` into `claimed` or `working` — a member claims it from the queue, or the lead assigns it — `groups.js` `postClaimLine` appends one short line to the room log in that member's voice, the one the room notice asks for: `接了 #1253，第一步是 <the card's note>`. The reference is the issue number the title carries (the title itself when it has none), the first step is the card's own note and never an invented one, and a card with no note still names itself. The line is appended to the log and **not** posted into the room's Session: no followup, no model turn, no round — the member's own work still arrives as its own-chat wake (#1205), and the two never merge. An identical line for the same card inside `CLAIM_CUE_REPEAT_MS` (30 minutes) is not posted again, so a re-claim stays quiet, and progress writes on a card the member already holds never reach the room: the claim is the beacon, the card is the progress. The record keeps the last cue as `claimCue` (`{ seq, at, text }`), which `view` leaves out. Tests: `core/test/claim-cue.test.js`.

A task may name where it came from (`target`, #1154): `task-create` and `track_tasks` take `https://github.com/<owner>/<repo>/issues|pull/<n>` or `<owner>/<repo>#<n>` and store `{ owner, repo, number, href }` with the href always on the `/issues/<n>` form; anything else is refused (`bot/invalid`). The target is optional, and a task without one behaves exactly as before: no `writeBack`, nothing extra on the card, no extra wake.

Deciding such a task leaves one comment for its Bot to post. `task-accept-result` and `task-send-back` set `task.writeBack = { target, at, state: 'pending', body }`; the body starts with `Accepted: <title>` or `Sent back: <note>`, carries the result summary, and ends with `Decided in FlyBot by <name>.` and `Decision by: <name>` — the person who decided, in a field of its own: `Written-by:` is the review attribution `review-gate.mjs` parses (#627), and a decision comment is not a conclusion, so no line of it carries that shape, not even one quoted from a note or a summary, and not through the decider's own display name, which is folded to one line before it is written (#1172). The host holds no token and posts nothing: the Bot that owns the task has the connector, so the comment goes out on its next turn. `track_tasks postResult { task, ok, error }` records how that went — `posted`, or `failed` with the one line the card shows (a failure without `error` is refused). Only the owning Bot may report, and only while the comment is pending or unconfirmed: one report per decision, no retry loop, and the decision itself stays recorded either way. A pending comment is work for the drive, but not for ever (#1172): only a wake that actually went out counts (`writeBack.wakes`), the reminder stops after two, and a day after `writeBack.at` the record turns `unconfirmed` — a quiet card line, not an error — instead of waking the Bot again. A task that is also real work keeps waking after the cap, and a report that arrives after that is still taken — `posted` or `failed` — so a comment that did go out clears the line. Tests: `core/test/tasks.test.js`, `core/test/bot-tasks.test.js`, `core/test/task-drive.test.js`.

`tasks` without a filter returns tasks the actor requested or whose Bot they own, including a descendant (`createdBy`) they do not themselves own. `tasks { botId }` is that Bot's list under the same rule. `tasks { roomId }` is the group view: a current human admin, or the owner of `room.admin`, sees tasks member Bots tagged with that group, and nobody else does. A room that never grew `participants` is read through `deriveParticipants`, so its `members` still count. A plain list does not include another Bot's group tasks. Names come back as `ownerBotName`, and a subtask also carries `parentTitle`. Tests: `core/test/bot-tasks.test.js`.

### Task-driven turns (#1109)

Unfinished conversation tasks wake the owning Bot. `src/host/task-drive.js` runs after a board write and after a turn ends. For each owner, the next task is the one `compareForWork` would name: `open`, `claimed`, or `working`, not `waitingFor: 'input'`, and not an overall group card (`kind: 'group'`). A decision whose comment is still `pending` counts as work even when the task is already `accepted`, and the wake says where to post it (#1154). That card is the plan; the subtasks are the work. One drive pass wakes every such owner, so a group assignment starts each member's own subtask in that same pass. An unclaimed queue item is offered, not driven (#1247): one idle member of its role that does not already hold a card in progress is woken in that member's own chat, one item per room and role per pass, one Session gets at most one task wake in a pass, and the cue carries the item's id, priority and title — not its note, which is the body. A claimed item is then a normal card above. One Bot still receives only its own next task. A task with no group wakes the Bot's own chat. The wake is a follow-up whose header is `[Continue task]` (`delivery.js`, role `task`). It names the task id, priority, and title. It is not a group post, so the reply is not posted back and does not start a round. A group subtask wakes that same own chat (#1205). It does not open the Bot's group Session and it does not start a round. The cue says to set the card's column and progress with `track_tasks`, not to post a status in the group, and not to wait for a confirmation. A question a person has to decide is one short post in the group; the wake's own reply stays in the chat and is not posted into the room. Completing or updating the card is what wakes the next assignee. The wake text also carries that room's compact board snapshot (#1203), the same one a round turn shows, so the Bot reads progress from the board. A Bot @ in the group whose open card already shows that line is a pass (`boardCoversCue` in `room-context.js`, applied in the round before a member turn): the round records it as passed and does not start a turn. A question, a line the card does not already say, and a person's @ still get a turn.

Tests reach the driver through `ctx.taskDrive` (`now`, `settled`, `consider`). That handle is a Cordis service registered with `provide`, the same path as `ctx.flybot`. A live context refuses a bare property write, which stopped startup before any Bot loaded (#1120).

The driver skips a Session that already has a turn, and a second wake while the first is still queued or in progress. A queued wake that has not started is replaced when a different task becomes that Bot's next one. A live group round does not defer that wake: it is not a group turn, so it does not sit beside the round. The parallel wake is the assignment pass. A wake that ends with the same board (status, progress, priority, note, title, who is waiting, and the state and target of a pending comment — not `updatedAt`, which a no-op `track_tasks` call still bumps) waits 30s, then 2min, 10min, and 30min before trying that Session again. A change on the board, or a person speaking in that Session, clears the wait. A queue offer keeps its own wait: the work pass and the queue pass compare different fingerprints, so one does not clear the other's backoff. A task that is waiting on an answer does not wake: the turn that called `ask` asks once, and the driver does not loop. The idle rule still forbids inventing work; unfinished work the user or a group already handed the Bot counts as that task. Tests: `core/test/task-drive.test.js`.

### A rate-limited turn is asked again (#1308)

A provider refusal that clears on its own — the requests-per-window `429` (`Limit type: requests`, `Remaining: 0`) — is not the turn's answer. `turns.js` `turn/end` asks the same trigger again after 2 s, 8 s and 30 s (`RATE_LIMIT_BACKOFF_MS`), through `delivery.js` `deliver({ rateLimited: true })`, so a group round keeps its waiter and a sender keeps its exchange; each attempt logs one line, and the attempt that outlasts them ends the turn once, in the `ended` failure line the chat already draws (#1044), carrying `rateLimited` with the attempt count. The provider's truncated `reset` is never parsed. A budget or quota refusal (`budget_exceeded`, `QUOTA`, 402) is not asked again. A round the person stopped while one of those waits was pending is not asked again either: the stop is noted before the backoff ends, its `turn/end` schedules no retry (`stoppedRoomTurns`), and the callback drops the wait when it carries that exchange, so no model call and no tool run happens behind a stopped round (#1679). `rateLimitRetries` is keyed by Session and holds one timer, so that drop forgets only the wait it belongs to: a newer turn in the same Session keeps its own retry, and a stop that removes a queued delivery keeps the exchange marked while a retry for it is still pending. A stop that lands after the retry went out is the running-turn path (`stopRoomTurn` cancels that turn), unchanged. Tests: `core/test/rate-limit-retry.test.js`.

### Work view step (#546)

`work.bots[id]` (`turns.js` `workView`) carries `step`: what the newest running call acts on, from its arguments (`command`, `cmd`, `pattern`, `query`, `url`, `file_path`, `path`, else `description`), whitespace collapsed and capped at 80 characters. It is in the owner-only Bot view (`authz.js` `ownedLive` picks the actor's own Bots), not in `work.rooms`, which other members of a shared group read. It goes with the call's result and the turn's end. Covered by `core/test/group-status.test.js`.

### Tool-call count per turn (#471)

`turns.js` counts a turn's `tool/call` events (the same events the activity feed folds; a program's sub-calls are not counted) and the count rides the work view: the running turn's count is `calls` on `work.bots[id]` and on its entry in `work.rooms[roomId]`, only while it is above 0; a turn that ended keeps its own count as `calls` on its `endedView()` entry. One place only — the Agent inbox reads the count for a card's own place (that Bot's own chat, or that one group) from those fields, never summed across places and shown as nothing for 0 or unknown. ### Work handed out from a group, in the work view (#553)

An own-chat turn that runs work a group member handed out with `message_bot` (`turns.js` `handedFromGroup`, the rule below that #550's group questions also use, exposed as `rt.handedFromGroup`) carries `fromRoomId` in `work.bots[id]`, so that group can show the work as its own while other rooms and the Bot's unrelated own-chat work stay apart. ### Questions about work handed out from a group (#550)

Work a member hands a Bot with `message_bot` from its group Session runs in a hidden turn of the Bot's own chat (the request carries `senderRoomId`), and the reply goes back to that member's Session in the group. `ask_user` in such a turn (`turns.js` `handedFromGroup`: role `request`, not `audience: 'user'`, not a friend's, the sender still has a Session in the room) does not write the Bot's own-chat card: it writes `state.questions[<room id>]` with `header` (the asking Bot's name), `botId`, `replyTo` (`{ botId, hop }` of the member that handed the work over), the asking turn's `origin` and `allowCustom: true`, so the card shows in the group's composer dock (the client's `QuestionDock` reads `questions[sessionId]`). One card per group: while another Bot's waits there, the tool tells the Bot to ask in its reply. `answer-question` on the room id calls `rt.answerGroupQuestion`: the answer reaches the asking Bot as a hidden `request` from the member (`fromRoomId` = the room, header names the group via `deliver`'s `answeredIn`), so its reply goes back to the group exactly as the work did and the Bot's own chat gets no card and no visible turn; the group shows a quiet notice (`<who> answered <Bot>: <question> → <answer>`). The answer keeps the asking turn's `origin` only when the Bot's owner gave it (fail closed: `other` for anyone else). A line typed in the group does not close the group's card (it goes to the group's round). `authz.js` limits seeing (`ownedView`) and answering/dismissing such a card to the asking Bot's owner or the room's owner. Deleting the room or the Bot drops the card. Face-to-face rooms take the same path on the local home. `ask_user` inside a group Session is still refused (the Bot asks in its reply, which the group shows). Covered by `core/test/group-work.test.js` and `core/test/authz.test.js`.

### Inbound shared rooms

- Bot Social conversations are 1:1; it does not list a FlyBot group. A leave envelope, hide, or grant revoke marks it left/hidden (#1167: the host sends that leave while the seat is still a live member, because reach and a room link's pairs only see current participants). The mirror then stays hidden: a later line is refused and a join that is not newer than that leave does not open it again; a newer join can. A hidden mirror sends nothing further. A projection is **named** from the envelope and **matched** by the transport (#873, #909): `applyInboundRoomShare` still shows `data.inviterName` (so a room carried here by a Chief's Bot reads after the person who invited it), but which room a share may touch is decided by `event.fromHome` / `event.fromHandle` — a share naming a room of mine while arriving from a home that room does not belong to is refused `not-inviter`, and the recorded `sharedFrom` identity only ever follows the transport, so an envelope can be displayed but never re-write whose room it is. Only `op: 'join` projects a room: a `line` envelope for an unknown remote room is refused `unknown-room` instead of opening one named by its own payload. A line keeps its own `who`, or the sender when it names nobody, never the inviter; its `authorId` follows the payload only when the handle traces to the transport sender, a remote seat of that room, or its inviter **from the home that invited the room** (#918 — the seat branch and the inviter branch now ask the same question) — otherwise the line is shown as the Bot that delivered it with `unverified: true`, and it is still kept so a forged claim cannot silence a message. The room match stays on the inviter handle alone, so a line presenting that handle from another home still lands and is only attributed to its sender: a room may match where a signature does not. Which room a share belongs to is recorded by a `join` alone; a `line` follows that record and never rewrites the inviter home or handle, or every message would make its sender the inviter. A room recorded before #873 may hold no inviter home at all, and then the only signature it keeps is the transport naming the sender itself (`claim === sender`); the next `join` records the home and the room stops being legacy. `reach()` allows a local member to message a remote that already sits in that room when `roomId` is on the send. Still not team mode. #904: the projection now records the host's side too. `recordInboundSharedRoom` keeps the guest's own Bot **and** one remote participant for the Bot that carried the join (`draft.inviterHandle`, with `admittedBy: 'ticket'` / `roomOnly` when a link seated it) — `invitedHandle` on this side names one of the guest's own Bots, so it is never recorded as a remote, and the friend path keeps its one remote. The rest of the host's room rides the `join` as `roster` and `notice`: `notifyRoomShare` sends `{ handle, home, name, ownerName }` for every Bot of this home in the room, and `{ name, ownerName, connected: false }` for one with no Bot Social identity; nothing of another guest's home is published, and the roster is re-sent whenever the host adds or removes a Bot of its own. `applyInboundRoomShare` reads a roster only when the envelope names this mirror's room (`data.roomId` = `sharedFrom.remoteRoomId`) and comes from its bound inviter, and merges it into the participants: one remote participant per entry (`fromRoster`, `roomOnly`), keyed by `(home, handle)` so two same-named Bots of different homes stay distinct, `verified` only for the seat or a published friend Bot. Verification is a signature, not a mention: an unverified entry is displayed and is not who a line may claim to be, an identity-less one is shown as not connected, and an @ of either — the title the @ menu inserts, or the roster name when it has no handle — still starts that Bot's turn on its own home (#949). A roster is the whole list, so a `join` that drops an entry marks it left (soft leave: the entry stays with `leftSeq`, history still resolves) and a re-sent `join` clears the mark; an empty `roster: []` clears the list, while a `join` without the field changes nothing. The notice is replaced by the next `join` that carries one; an explicit empty string clears it and a missing field leaves it. #923: the one pair a room link opened is enumerated even when the seat record predates it. A seat a link admitted is a pair through its own `admittedBy: 'ticket'` / `ticket`, and, when that record is older, through the link's own `homes` — the home-to-handles map the accept writes and keeps — reached from the Bot whose handle it knocked on, or from the room's lead when the seat did not even keep that. So a group envelope from this home reaches that guest as the room's traffic (`sendTicketShare` names the room the link was minted for) instead of falling back to a friendship the two homes never had; a friend's Bot added by hand is named by no link and stays out. This is FlyBot's half of the pair: Bot Social still decides at send time, so a room-started conversation it refuses needs the server-side fix.
- A Bot named in a shared room answers in that room (#825). `fanoutRoomLine` (`src/host/room-membership.js`) puts the calls a line makes in the envelope's `calls` (resolved where the room's mentions are resolved: the social handle, the roster name, and the title the @ menu inserts, so `@Chief (owner)` and `@Data (Friend)` name the same Bot a bare name would; a Bot with no social handle is called by that roster name, and a `not-connected:` id is never a token — #949). A fenced or quoted `@name` stays literal text. The envelope also carries the line's `hop`: a person's line is hop 0 and a Bot's answer is one hop on. The receiving `applyInboundRoomShare` keeps only the calls that name this room's own Bot (`localCalls`), opens **one** turn for each through `rt.startInboundTurn` (`groups.js`: `participant.open` + `participant.runTurn` + `appendRoom`), and skips it when the line's hop has reached the room's `maxHops` (kept on the room, `DEFAULT_MAX_HOPS` 3) or when the same remote line was already answered — the last 200 keys `remoteRoomId:seq:botId` live in `room.answered`. That turn's answer is an ordinary room line, so `fanoutRoomLine` sends it back to the inviter as an `op: 'line'` envelope under the *inviter's* `roomId`, one hop on; an answer its owner's approval holds or refuses still shows as one `notice` line in the room instead of silence. Remote text stays inside the `fencedUntrusted` fence.

### A local room's invite link (#852)

- A room that lives in FlyBot can hand out one link: `https://social.botawaken.com/r/<inviter Bot handle>/<ticket>`. `core/src/shared/room-share.js` `parseRoomInviteLink` reads both shapes in the one invite field and says which one it saw (`{ kind: 'local', handle, ticket }` / `{ kind: 'face', ticket }`), and `roomInviteUrl` builds the local one. The ticket is `randomBytes(16)` in base64url — 22 characters of `[A-Za-z0-9_-]`, inside the 64-character shape `FACE_INVITE_TICKET` already accepts. The handle is its own path segment because `send_as_member` addresses a Bot by handle, and a ticket cannot carry one inside that limit.
- The room record is the only authority: `room.localInvites [{ ticket, handle, botId, expiresAt?, mintedAt, mintedBy, server?, url?, homes?, acceptedAt?, withdrawnAt? }]`. A link has **no deadline and is not single-use** (owner decision 2026-10-24, #892, Bot Social #65): anyone it is given to can join with it, each home once (`homes: { [home]: [seat handles] }`; a record from before keeps its one `acceptedBy` / `seats`, read through `homesOf`), until the owner withdraws it or the room is deleted. A link minted with an `expiresAt` (an older Bot Social, or before the change) keeps that deadline. Several may be live at once (#878); a record written before the list (`room.localInvite`) is moved into it on first read. `rt.mintRoomInvite(roomId, actor)` adds one (dead links that seated nobody are dropped then); `rt.localInvitesOf(roomId)` lists the open ones (not withdrawn, not out of date; a link someone joined with stays open) and `rt.localInviteOf(roomId)` is the newest; `rt.roomOfLocalInvite(ticket)` resolves the room from the ticket; `rt.revokeRoomInvite(roomId, ticket?)` withdraws one link, or without a ticket every open one: it sets `withdrawnAt` (nobody new joins; the server ticket is revoked without `endClaims`), the seats it made stay, and a withdrawn link that seats nobody is dropped. A shared (`inbound-share`) or face-to-face room refuses to mint — it has its own invitation.
- Three steps on the same envelope, answered by the room record: the invitee's host sends `{ op: 'ask', ticket }`; the inviter answers `{ op: 'invite', ticket, roomId, name, lead, expiresAt }`, which is information only (it consumes nothing and seats nobody); the accepting knock `{ op: 'ask', ticket, accept: true }` runs verify → consume → add → the existing `join`, which `addRoomParticipant` sends. `applyInboundRoomShare` handles both ops **before** the branch that projects a room for an unmatched `join` / `line`, so a knock never conjures a room; `parseRoomShare` accepts `ask` without a `roomId` and requires one on `invite`. The asker is `event.fromHandle` (the transport's sender), never a field of the payload. The accepting home is added to `homes`: the same home retrying is idempotent success (the lost `join` reply is sent again) and another home may join too (#892); an add the room refuses removes that home again. Refusals are local on the inviter's host (`unknown` / `revoked` / `expired` / `no-sender` / `not-addable`) and change nothing. The UI half — the Members card's **Invite by link** row and the dialog the offer draws — is still to come. Covered by `core/test/remote-room.test.js` (#852).
- The endpoints the UI calls (#876): `room-invite` reads the live link (`rt.localInviteOf`, what the Members card copies and counts down), `room-invite-mint` and `room-invite-revoke` are the room owner's or a human admin's call (`authz.js`), and `room-invite-ask` is the invitee's side: `rt.askLocalInvite` reads the handle and ticket out of the link and sends `{ op: 'ask', ticket }` from one of the actor's own Bots whose home has a Bot Social identity — the link cannot name a sender, so the transport does, as on the answering side. Join is the same call with `accept: true`, and the answer arrives as `invite` through `applyInboundRoomShare` (`rt.onLocalInviteOffer`). A face-room link, a bare ticket and a ticket outside the 16–64 shape are refused in one sentence and send nothing; the knock carries no `roomId`, so an invitee can never name a room it has not seen.
- Strangers (#884, #878): when the social plugin registers Bot Social's ticket record (`flybot.rooms.serveInvites({ identify, mint, preview, claim, verify, revoke, endClaim })`, `rt.roomInviteServer`), a mint goes to the server (`server: true`; a server that fails refuses the mint — it is never swapped for a local ticket — and one without `local_room_invites` answers `undefined`, which keeps the friend-only local ticket). The link knocks on `invite.botId`, the room lead when it has a Bot Social identity; a lead with none gets one first through the seam's `identify` (the link is the owner's consent, as accepting a friend's invite is), and so do the Bots a guest brings on Join. A room-only identity (left by a face-to-face room) counts as none (#899): it is not polled and cannot send the knock, so `identify` promotes it, and when the seam is registered `rt.identifyInviteBots` promotes the Bot of every server link still open or holding a seat. `room-invite-preview` answers `roomId` and `joined` next to `claimed`: a claim is not a seat and a seat is not a claim — `joined` is true when this home holds the room, matched by that link's ticket or, since #1176, by `sharedFrom.remoteRoomId` for a room the host added one of these Bots to by add-member (no ticket), so a link for a room already here is not reported as a knock. On the invitee's side, Join (`room-invite-ask` with `accept: true` and `bots`, the invitee's own Bot ids) claims the ticket at the server for those Bots, all or none, then the first of them sends `{ op: 'ask', ticket, accept: true, roomId, bots }`; `room-invite-preview` (`rt.previewLocalInvite`) reads the server's public record before Join. On the inviter's side the knock is only a request: `seatByTicket` reads the claims back with this home's own credential (`verify` → `claimers`, every home that joined; an older server's single `claimer`) and seats exactly the Bots of the claim that brought the asker, from that home, in this room, or nothing — refusals `unclaimed` / `claimed-elsewhere` / `wrong-room` / `lookup-failed` / `expired` / `revoked` / `not-addable`, each its own. A seat is `{ remote: true, admittedBy: 'ticket', ticket, hostBotId }`: no published friend (`publishedRemoteOf` stays empty, nothing in the sidebar), and `notifyRoomShare` / `fanoutRoomLine` reach it from `hostBotId` only, with `meta.scope` = the room id so the transport sends it under that room (Bot Social's room reach). Withdrawing a link does not end its seats (owner decision on #853). One projected room holds every Bot a ticket seated (`sharedFrom.ticket`; each `join` adds or revives only the Bot it names) and the owner as a human participant, so the person the link admitted can write there; a person's own line goes under their Bot Social owner name when this home only knows them as `You` or their member id (`seatSayer`, both directions). Ticket lines carry the text as written (`seatText`: a stored fence is opened, never nested) and the receiving home fences it once. a seated Bot's line goes from that Bot under the inviter's room id, and the last of its Bots leaving gives the claim back at the server. Reach: `reach.js ticketPeers(state)` lists the only pairs a link opens — `{ from, to, scope, ticket }` for a seat here (from its `hostBotId`), for a room of another home that seated Bots of mine (from those Bots to its inviter), and for a claim this home made (`state.roomClaims[ticket]`, the accepting knock's way out, dropped when the last seated Bot leaves or after a day unanswered). `reach()` allows a local → remote send that matches one exactly under `meta.scope` (the exact handle, never any Bot of that home), and the social plugin reads the same list (`flybot.rooms.ticketPeers()`) for its transport. A seat is enumerated from the link's own record of who it admitted, and `reach.js` reads that record through `homesOf` (`room-membership.js`) — one reading, used by both halves, so a link accepted before `homes` was written (`acceptedBy` + `seats`) enumerates the same pair and a room that predates the field does not lose it (#929); `linkSeats` stays read-only, writes no state and sends nothing. A join also carries `history`: the recent chat lines (`who`, `authorKind`, `seq`, unwrapped text, and a Bot's handle when this home has one). An absent field does not backfill (an older host); an empty list means there were no chat lines. The guest copies them into the mirror once, only while that log has no chat lines yet, and does not start a turn for them (`applyShareHistory`). A line that arrives after the join — on the guest mirror (`applyInboundRoomShare`) and on the host room (`ingestSeatShare`), and a guest Bot's own reply from `startInboundTurn` — is posted into the room Session with `rt.showSharedLine` (`displayOnly`). The conversation pane is that Session; `room.log` alone only feeds the sidebar preview, because the channel view strips `log`. The followup is not appended again, so it does not fan out a second time, and `openingSpeakers` returns nothing for it, so a name in the text does not open a round. A redelivery of the same remote seq does not draw a second bubble (`room.shownShare`). #1064: the knock is not the only way those seats are made. The social plugin's inbox poll calls `rt.seatOpenClaims` (`flybot.rooms.seatOpenClaims`), which `verify`s every open server link and seats each claiming home the same way, then sends `join` only for a seat whose notice has not yet left (`invite.told`). A lost, denied or unread knock still seats the guest, and the `join` opens the group on the guest's sidebar. A room that cannot be shown (`not-addable`), a notice waiting on approval (`held`) or one that does not leave (`not-delivered`, after a few tries) keeps `waiting` on the link (`reason`, and for `not-addable` the local Bot names). The Members card says so, and **Seat them** calls `room-invite-seat` (the room admin, same rule as mint), which runs that read again with the tries reset. #1161: a quiet poll reads one open server link about once a minute and, when the preview says `Too many attempts` (or answers `rate_limited` / `locked_out`), waits out the minutes that sentence names or the `Retry-After`, up to 10 minutes, so a home that stays open does not preview again before that cool-down elapses; **Seat them** and a read of one room still verify at once, and a preview that did not answer is tried again on the next tick. A seating send that is still `pending_approval` is `hold` and is not recorded as told; one whose hold is not listed yet is retried as not delivered. Covered by `core/test/room-ticket-seat.test.js` and the `#923`/`#929` cases in `core/test/remote-room.test.js`.

### A burst of the user's lines (#642)

- Channel `send` in the Bot's **own chat** (no room on that Session) collects the user's lines: the first line that arrives with no turn running starts a 1500 ms `SETTLE_MS` timer on that Session (`channel.js` `settleLine`), further lines inside the window join its text, and the timer opens **one** turn carrying them in arrival order, each on its own line. ### Out-of-app delivery, first half (#355)

- A reminder has to reach the owner with the desktop app closed, so its delivery cannot be a client toast. `src/host/notify.js` is the adapter that half needs, and nothing calls it yet: `schedules.js` wiring is the second half, once a real channel exists.
- `createNotifier({ transport, channel })` speaks Slack's `chat.postMessage` shape — `postMessage({ channel, text, blocks?, threadTs? })` → `{ ok: true, ts }`, or a typed `{ ok: false, error }` — with the transport injected. The production Slack transport waits for the owner's credential and is not in this repo; `fakeSlack(script)` is the stand-in the tests run on, recording every call and scripting each answer (a function or an `Error` too), and `rateLimited(ms)` / `channelNotFound()` / `networkFailure()` spell the three failures.
- Delivery policy: one key per reminder, so the same reminder handed to `send()` again after it went out answers `duplicate` with the first `ts` and never reaches the transport, and one handed over while it is in flight joins that attempt. A retry waits `min(base · 2^(n-1), max)` — 500 ms then 1 s by default — and `retryAfterMs` from a 429 is a floor, never a ceiling: waiting less only earns another 429. Three attempts at most; running out is not a verdict about the channel, so a later call may try again.
- A structural failure (`channel_not_found`, `not_in_channel`, anything untyped) is permanent: one call, `permanent: true`, and a second `send()` for that key is answered without another call. A thrown error and `network` are the same broken link: retryable.
- `enabled` is checked before every attempt, not only at the start, so switching a channel off stops a reminder that is already waiting out a backoff, and a channel that is off makes zero transport calls. Sent keys are capped at 1 000 process-local entries; nothing is persisted, so a restart forgets them and at-least-once survives a crash.
- `core/test/notify.test.js` drives every retry with fake timers, needs no network and no key.

A bare `capability_not_granted`, or the same code naming another capability, is not that fact (#988). No line carries *Try again.* twice (#954).

## Busy-send acknowledgment (#1584)

When a person's line reaches a Bot's own chat while that Session already has a live turn, the host records a short spoken acknowledgment on the live payload (`busyAcks`) — at the line's arrival, which DSH appends as `agent/inbox/spliced` whose `inserted[].source.kind` is `user`; the line's `user/message` follows only at the next step's start, when it is claimed, which production logs put up to 768 s later, so the claim is the fallback for a splice that was not seen — except for the line that opens a turn: DSH appends `turn/start` before the step's `user/message` (agent-loop `index.js:943` then `:1061`), so that line is claimed while the Session already reads as running, and the host skips the first claim after `turn/start` instead of acknowledging a message that started the turn ([#1698](https://github.com/ThinkFlowLab/FlyBot/issues/1698)). The line's own message id is what keeps one line from earning a second ack and a second model call: the host keeps a per-Session ledger of the ids it has acknowledged, beside the ack entry rather than inside it, because the entry dies at `turn/end` and the claim of a `next-turn` line always lands after it ([#1684](https://github.com/ThinkFlowLab/FlyBot/issues/1684)). The ledger is bounded on both axes. Per Session it keeps `LINE_IDS_KEPT` ids exactly, folds anything older into a fixed-size 1 KiB filter (three salted positions per id), and rebuilds that filter from the exact set every `LEDGER_FILTER_REBUILD_AFTER` folds — a filter that only ever filled would answer "acked" for 3.6% of brand-new lines after 1000 lines and 97.9% after 12000, which silences the ack again, so the guarantee is the last 16 lines exactly plus under 1% worst-case false positives on older ones, and a pruned id still answers "already acked" and cannot resurrect a line, while a stale claim finds no ack entry to reopen ([#1678](https://github.com/ThinkFlowLab/FlyBot/issues/1678)). The Session map is bounded too (`LEDGER_SESSIONS_KEPT` Sessions, the one that wrote longest ago dropped), so an archived Session cannot hold its memory for the life of the process ([#1684](https://github.com/ThinkFlowLab/FlyBot/issues/1684)). An own-chat `next-step` splice — a steer, admitted at the running turn's next step — is not ack'd. A person's line relayed into a running member's group Session (`role: 'room'`, no Bot sender) earns the same one, keyed by that member Session and published per member on the room as `busyAcks` so the room draws it on the member's row ([#1646](https://github.com/ThinkFlowLab/FlyBot/issues/1646)); a mid-line there is relayed as a steer (`groups.js` `steer: true`), so it is spliced for `next-step`, and the member's row is acknowledged at arrival like an own-chat line rather than waiting for a claim ([#1684](https://github.com/ThinkFlowLab/FlyBot/issues/1684)). The line is written by one short model call on the host ([#1665](https://github.com/ThinkFlowLab/FlyBot/issues/1665)), replacing the templates of [#1629](https://github.com/ThinkFlowLab/FlyBot/issues/1629) that quoted a clipped piece of the message inside a fixed phrase: the ack is published at once with an empty text (the client draws the avatar with blinking dots), then a separate call — `config.flybot.modelFor['busy-ack']` when set, else the chat's own model, reasoning off when the model offers it, `ACK_MAX_TOKENS` output — is asked for one natural sentence in the message's language that shows what the new message is about and what the turn is doing (its running tool and the request it works on), with no quoting and no stock phrases. A hard `ACK_TIMEOUT_MS` (3 s) bounds it; a timeout, an error, an empty or overlong answer, or no model route leaves the text empty, so no sentence is ever sent and the dots clear with the turn. A late answer never revives a cleared ack. The client draws it as one bot bubble (and also from a local pending queue/steer submission) so the chat is not silent while a blocking job wait holds the next step. Related but separate: [#1509](https://github.com/ThinkFlowLab/FlyBot/issues/1509) (Steer does not abort a tool wait). Host: `core/src/host/busy-ack.js`. Client: `core/src/client/busy-ack.js`. Tests: `core/test/busy-ack.test.js`, `core/test/busy-ack-arrival.test.js`, `core/test/busy-ack-ledger.test.js`, `core/test/busy-ack-client.test.js`.

## Steering interrupt: a wait over 60s yields to a human send (#1509, #1666)

Steer alone admits a human line only at the next step boundary, so a foreground `bash`/job wait that blocks the step keeps the line waiting for the wall clock. `core/src/host/steering-interrupt.js` watches the Session events itself: a `tool/call` (or a program sub-call) is an open wait from its `event.time`, and `tool/result` / `turn/end` close it — a result names its call on `data.message.toolCallId`, the shape the host writes (#1644), and `data.callId` only serves older payloads, so reading it alone left every wait open and turned the 60s line into the turn's age. A person's line arrives as `agent/inbox/spliced` the moment DSH queues it, and its own `user/message` only follows at the next step, after the blocking tool returned (#1666); both arrivals are judged, and the let-go clears the open wait, so the later one is never a second interruption. When such a line from source `user` lands in that Session while it is the Bot's own chat, a turn is live, and the oldest open wait is more than `INTERRUPT_AFTER_MS` (60 000 ms) old, the host cancels the turn the way Stop does — `agent.cancel({ kind: 'hook', reason: 'ds-bot/interrupt-long-wait' }, { keepInbox: true })` — exactly once per wait. `keepInbox` is what makes the send safe: the abort ends the turn, and the human line survives in the inbox for the turn that starts right after, so it is claimed at once and never lost. Waits of 60s and shorter are left alone, a finished wait is not a wait, and a group room or an idle Session is never touched. The threshold is fixed; no settings key. Tests: `core/test/steering-interrupt.test.js`.

A group room takes the same 60s line, through the room's own path (#1650). A person typing in a room lands on the room's own Session (`room.id`), not in the member's, so the own-chat gate never saw it and the member's turn held the round for the whole wait. Now, when such a line (the splice, or the `user/message` that follows it) lands on a room's Session, the member turn the round is waiting on is live, and that member's oldest open wait is more than `INTERRUPT_AFTER_MS` old, the host lets the turn go through `stopRoomTurn(sessionId, exchangeId)` — the very cancel Stop uses, `{ kind: 'hook', reason: 'ds-bot/stopped' }` with no `keepInbox`, so nothing the member had begun reaches the room, exactly as after a Stop. The line is safe because it waits in the room's queued inbox, and the next round answers it. A room id never takes `reason: 'ds-bot/interrupt-long-wait'`; that reason stays the own-chat one. Only the member the round is waiting on is let go — another member running in the same room is untouched — and waits of 60s or less, a finished wait, and an idle Session are all left alone.

- **Pickup after a restart** (`resume.js`): every running Bot turn and every delivered-but-not-taken message is noted in `inflight.json`. At the next start a noted turn is picked up once only if a restart really cut it: the durable Session log's `turn/end` for that turn is `interrupted` (or an abort caused by `disposed`, or there is no end). A turn that finished while this plugin was not listening — `completed`, `blocked`, `max-tokens`, `forked`, or aborted by the user / hook / parent — is not repeated; a `turn/start` seen after the start means the noted turn ended too. Notes from a build before the record carried `turn` keep the old behaviour. A pickup is confirmed before its note is dropped: the notes read at start are seeded into the live `turns`/`queued` (so the file keeps everything still owed), a turn's note stays while its pickup runs and is dropped only once handed over (unless the resumed turn has written its own note first), and a queued message whose resend fails is kept for the next start, an exchange is noted once (a resend delivers the `exchangeId` the notes already hold, and noting it again left a copy behind after a turn took it up, so the start after that sent the message once more), and a turn taking up a message forgets every note of its exchange; a crash or a failed delivery during the pickup no longer loses the work — a pickup is at-least-once, not once: a crash between handing the turn over and the write that drops its note repeats that pickup once, because the `taken` set and the inbox that would tell the next start otherwise are process-local. That is the safe side of the trade, a repeated turn the user can see instead of work the user was told about going silently dead. Covered by `core/test/follow-through.test.js`.
- A repeated Bot-to-Bot line becomes one turn (#641): `deliver()` keys the last 60 s of Bot-to-Bot text by sender + recipient Session + the text with its whitespace collapsed (`DEDUPE_MS`, `duplicateDelivery`), drops a repeat before it is recorded as an exchange or handed to the Session, and journals the drop as `delivery: dedupe <sender> -> <session>` in the host warning log. The key includes the Session, so the same line to another Session (a group copy, another Bot) is its own delivery; `deferred` / `resumed` / `retried` / `resent` carry on a message the Session already has and are never judged, and a friend's line, the user's own message and a group round are not Bot-to-Bot. Routing (parent and direct children) and the existing unread-queue refusal are unchanged, and the map is process-local and capped at 500 entries. Covered by `core/test/repeated-delivery.test.js`.
- **The check line is 45% of the usable window, not 80%** (`steward.js` `linesFor`): a Bot's conversation is condensed once its estimated size passes `DEFAULT_CHECK_RATIO` of the model's declared window less the room its reply needs, so the conversation is condensed earlier than upstream ds-bot does. The share is a floor on the prompt of a long turn, because every call re-sends the fixed block and the history is most of each prompt (#796); the trade is a checkpoint sooner and less detail kept (#1233). `checkRatio` in the profile still sets the share, and the hard line stays at 95% of the usable window, so a share at or above 0.95 can never lift the check line above it. Covered by `core/test/steward.test.js`.
- **A checkpoint is judged by the prompt that is left** (`parts.js` `pressureLeft`): the token meter stays anchored on the provider usage from before the span was replaced, and its surface delta only subtracts a 4-characters-per-token estimate of the removed text. A denser report — the mock's 3 characters per token, or CJK on a real model — can therefore still read above the check line after the checkpoint has replaced the span, and the part would move on even though the steward said to condense in place. After a compaction, the part stays when the heuristic size of the remaining surface plus the tool schemas is under the check line. A surface that is still over it moves on, as before. The decision to cross the line in the first place still uses the anchored total (#917).
- **The steward is asked again before a part moves** (`parts.js` `decide`, #1447): its one answer decides whether the part moves, and a rate limit on that request — a per-minute count on the same key the conversation uses, recovered in seconds — used to read as "no answer" and moved a part that was still working: a fresh Session, the latest messages re-sent, a note written through the same limited key, and a handoff whose reason said "the previous part grew long". A route reports a failed request as a terminal finish chunk, not as a thrown value, so `askSteward` carries that chunk's `failure` — its `code`, `status` and `providerRetryAfterMs`, not only its message — onto the Error it throws (`stewardFailure`), and the classification below reads exactly those. A failure that can pass (rate limit, timeout, 5xx, by `RATE_LIMIT`/`SERVER`/`TRANSPORT`/`TIMEOUT` or by a 429/5xx status) is now retried up to `STEWARD_ATTEMPTS` (3), waiting the `providerRetryAfterMs` the provider names (capped at `STEWARD_RETRY_MAX_MS`, 5 s; the raw adapters' `retryAfter` is seconds and still read) or a short backoff that grows by attempt; a success at any attempt is the answer. Below the hard line a failure that outlasts the attempts spends the round instead of the part: the part stays, and the next round asks again only after `STEWARD_COOLDOWN_MS` (60 s, then 300 s, counting failures in a row). Over the hard line, and for a failure that retrying cannot change, the part still moves on; `segment.steward` then records the failure and the handoff says `the context steward could not be asked whether to keep it (…)` rather than the default reason. A note's own retry (`NOTE_ATTEMPTS`, `NOTE_COOLDOWN_MS`) is a separate policy and unchanged. Covered by `core/test/steward-retry.test.js`.
- **Making room before a step has its own deadline** (`parts.js` `condense`, #1285): the pre-step overflow compaction used to carry only the turn's own signal, so a summary request stuck in retries — a 429 storm retries each request five times with its backoff — parked the turn before its first step: no `step/start`, no `turn/end`, `load: 1` and the roster's `stalled` hint until a human called `stop_bot`. `COMPACT_DEADLINE_MS` (`config.compactDeadlineMs`, 300 000 ms) now bounds that call through `AbortSignal.any([signal, deadline])`. When the deadline is what ended the wait, `condense` warns `ds-bot: making room for %s ran out of %d ms before a step; the turn ends here and the next one tries again: …` and rethrows, so DSH's own `finally` appends `turn/end` and the turn fails normally. DSH claimed that step's input before the pre-step hook ran and does not hand it back for a turn that ends in an error, so before the throw the deadline branch queues the batch again (`keepClaimed`, `agent.inbox.append('next-turn', …)`, one ordinary queued message each, a copy the inbox already holds refused): nothing the turn was woken for is lost, and the next turn — which the loop starts straight away while input is pending — reads it and tries to make room again. A provider that stays down therefore fails one turn per deadline, back to back, each ending normally instead of parking at `load: 1`; no backoff is added here, the queue is the thing that carries the work forward. A turn the user aborted keeps the old path (warn, `false`, move on), and the `!signal?.aborted` half of the guard keeps a turn the user stopped in charge even when the deadline was already reached. The idle pass is unchanged on `NOTE_TIMEOUT_MS` (600 000 ms, one shared signal over both note attempts). The turn-ending waits stay where they were: steward 120 s, idle condense and the handoff note each at that same 600 s budget. Covered by `core/test/pre-step-compaction.test.js`.
- **A part is committed before its handoff runs** (`parts.js` `moveOn`): the Bot's `sessionId` / `room.sessions`, the new segment and the `rescued` mark are saved first, so the turn the handoff starts can never see an uncommitted part — a failure handler that did would start a second switch against it and lose the previous part's note, and the rescue would not know it may only happen once. The handoff package is written next; if that fails, the pointer is rolled back (best effort saved, the fresh Session archived, the rescued mark dropped), so the old part is current and the finalizer hands the input on there. Two windows stay open, and both are written down rather than discovered later: a crash after that save and before the handoff package is flushed leaves the fresh part current with no package — the stopped turn's input still goes to it, so no work is lost, but the note is, and the rollback never runs; and the rollback's own save is best effort (`rt.save().catch(() => {})`), so a failing rollback leaves the file showing the fresh part while memory holds the old one, and the next start behaves like the first window. Neither is a reason to clear the pointer before the save: a note lost this way is a part without a handoff note, while clearing first loses the handoff package itself. The move is marked done only after the stopped turn's input and the old inbox messages are forwarded; a switch that never starts (no place, another switch, a read-only host) lets the step continue instead of rejecting its messages, which DSH has already taken out of the inbox. An armed scheduled task keeps the earlier Session active and DSH refuses to archive it, so the switch keeps the `moveSchedules` promise and waits for the move before archiving the earlier part; when the move failed and the refusal reports `schedule` as the only activity, the plain archive is retried with `{ stopActivity: true }` (the way a deletion does, `roster.js:450`), so a finished part is never left active with a task nobody sees; a refusal caused by a job, turn or subagent is never answered with `stopActivity`, because that would stop it too (#896): the id is remembered instead and the archive is asked for once more, with no options, when that holder is reported ended — the job registry's `settled` event for a job, the Session's own next `agent/status` idle otherwise — keeping the id while a refusal still names one of them, and holding at most 32, oldest dropped (#1433). Covered by `core/test/work-dir.test.js`, `core/test/part-archive.test.js` and `core/test/bot-messages.test.js`.

### Connectors: GitHub, the Composio gateway, and the Feishu sender (#311, #1263)

`src/host/connectors.js` mounts one MCP server per connector through DSH's own MCP client, so a Bot's tools are `mcp__github__*` and `mcp__composio__*` **for the owner's own use of every Bot, and for other people's use of a Bot only when the owner allowed it** (per-Bot access, below). Composio is a gateway: one API key (`COMPOSIO_API_KEY`) and a list of apps the user picked; the host asks Composio's tool-router for a session limited to those apps (workbench off) and mounts the session's MCP address. The session is made once per connect or app-list change and kept as `state.connectors.composio.session` (`{ id, apps }`: never the key and, since #335, never the session's address): the key check, the mount and Try again reuse it while the apps are the same and `GET /tool_router/session/{id}` (`x-api-key`) still finds it, else a new one is made. The mount's address is the `mcp.url` that answer carries (Composio's reference lists it as required in both the create and the get answer), taken only when it is https on the API's own host and held in memory for that mount; a session whose answer names no usable address is treated as gone. Why the address is not stored (#335): Composio's docs show the session address always used together with the key header and say to treat the exported address-and-headers config as a secret, but they do not say the address alone cannot authenticate, so it is not kept in `state.json` (backups, exports and anything that reads the profile) and is rebuilt from the id and the key at each mount. A record an older version wrote with `url` is rewritten without it at start (`scrubAddresses`), and the in-memory address is also taken out of a connector error (`[session address]`) before it is shown or logged. A superseded session (the old one after Choose apps or a new key, the new one when saving it failed, the kept one on Disconnect) is deleted with `DELETE /tool_router/session/{id}`, using the key it was made with; the delete is best effort and never an error for the user, and stopping the host leaves the session for the next start. Composio asks for each app's sign-in the first time a Bot needs it, in the chat. A stable `flybot-<uuid>` user id kept in `state.connectors.composio` (kept across Disconnect) is what Composio ties signed-in apps to. Rules: the key is a secret kept for all of the owner's Bots like any key the owner saves (#545; until then a connector saved it with scope `[]`, no Bot's shell), sent only as the `x-api-key` MCP header and to the API address, never written to `state.json`, a profile or an error (errors go through `redactSecrets`); the API address must be https, the answer's MCP address must be https on the API's own host, and the session request does not follow redirects; the key is proved by creating the session before it is saved; `connector-apps` changes the app list without the key and keeps the old list when Composio refuses the new one; `connector-app-search { id, query, token? }` searches Composio's app list (`GET /toolkits?search=&sort_by=usage&limit=20`, `x-api-key`, no redirects) with the pasted `token` when given (not saved) or the saved key, and returns only `{ slug, name }` with slugs a session can take; `connector-app-status { id }` reads the kept session's apps (`GET /tool_router/session/{id}/toolkits?toolkits=…`) and returns `{ [slug]: 'ready' | 'sign-in' }`, ready when the app needs no sign-in or has an `ACTIVE` connected account (#359); `connector-*` writes are `SHARED_BLOCKED`; `github` and `composio` are reserved capability names; `composio: false` hides the connector. Which Composio tools run without asking is DSH's normal tool approval, not a FlyBot gate (a per-app approval is a later step).

Feishu (Lark) started as the first **sender** connector (#1263), and its webhook mode still is one: a group's custom-bot webhook is one HTTPS POST into the instance's own group, so nothing is mounted, no Bot's tool list changes, and `connector-access.js`'s `CONNECTOR_IDS` does not list it. The definition is a channel today, not a sender (#1266, below): the view reports the kind and the client reads it instead of hard-coding an id, and the channel kind is what makes the row offer Choose Bots and `reconcile()` open the socket, while webhook mode is the same row with nothing to dial. A webhook stops at the status: a saved webhook reads `ready` without posting, because the test POST belongs to the **connect** step, so a restart never messages the group; `connector-retry` ("Try again") is the one path that proves it again. The webhook is `FEISHU_WEBHOOK`, saved through `secret-set` **before** the probe — so a refusal stays on the row as `error` with the reason and `redactSecrets` can mask it, the way a failed mount does for GitHub — and it must be https on the configured `feishu.api` origin, else `A Feishu webhook must be https on <origin>`: the URL is the credential, so it may never be posted to another host and never appears in `state.json`, the view or a warn line. `connector-send { id, text }` posts one message on demand and records `lastOkAt` / `lastError` in `state.connectors.feishu`; nothing posts room traffic by itself. Feishu answers HTTP 200 with the verdict in the body (`code: 0` success, `9499` a rate limit, `19021` a refused signature), so `feishuPost` maps the body into notify.js's vocabulary and the retry policy stays `notify.js`'s `createNotifier` (3 attempts, backoff, honour `retry-after`, structural errors not retried) rather than a second one written here; `connector-send` uses a fresh idempotency key per call, so two messages with the same text are two messages. The connect probe and a send both carry a deadline (15 s and 60 s) and `withDeadline` races the fetch, so a fetch that ignores its abort signal cannot hang either. `feishu: false` hides the row; `connector-send` is in `SHARED_BLOCKED` like the other connector writes.

The same row carries a Feishu message coming **in** (#1266): `inbound` reports `off|connecting|ready|error`, the last event, the last error and whether the app pair is `set` or `missing` — never a value. `src/host/feishu-inbound.js` owns the policy: off unless the row has app mode connected with both halves saved (`mode: 'app'` on the record and an app pair `appOf()` can assemble, below — no config switch of its own), so an off connector dials nothing. The owner is the only sender that may start a turn: `feishu.ownerOpenId` from config is one half of that gate and the record's `allowed` guest list (below) the other, and an empty `open_id` never compares equal to an unset owner. A bounded ring of 512 `event_id`s makes a replay land once — the id enters it only after `deliver` has returned, so a handover that threw is retried instead of being refused as a duplicate for ever — and one socket per connector shares a start. The socket itself is injected as `rt.feishuTransport` (`connect(onEvent) -> { close }`) so the client behind it is one adapter, and it is read again on every start rather than copied while the modules install — an adapter that arrives later comes up on the row's **Try again**, which retries the sender and the socket together; a stop that lands while a socket dials hangs up the one that arrives instead of adopting it. `src/host/feishu-sdk.js` is the default adapter over the official `@larksuiteoapi/node-sdk`, imported only when a socket is dialled and reading the app pair at that moment, so a host that never turns the long connection on pays nothing for the package; the message lands through `remote-chat.deliver`, the seam a friend's Bot already uses, and the answer leaves again through the sender this module registers in that seam under the `feishu` plugin, posting on the same `FEISHU_WEBHOOK` `feishuPost` has used since phase 1 (a chat an older build opened without the plugin is refreshed on its next message) — one path in, one path out. `FEISHU_APP_SECRET` is the only half read as a secret through `rt.secretValue`, the App ID travels in the connector record (below), and a half-saved pair reports `missing` and dials nothing.

The connector row is where Feishu is configured (#1266, owner's word 「飞书是做成一个连接器，左下角点击连接应用的时候可以连接」), so the definition is no longer one secret and one mode: `feishu` is `kind: 'channel'`, declares `credentials` (`FEISHU_MODES` — a custom-bot **webhook** with one masked URL, outbound only as phase 1, or a self-built **app** with App ID + App Secret) instead of the singular `secret`, and `reconcile()` branches on `kind` — a channel is a socket whose lifecycle is the row's status (`off|connecting|ready|error`), while every other connector is still an MCP client. App mode proves the pair with one `POST /open-apis/auth/v3/tenant_access_token/internal` that is then discarded (the socket dials with its own credentials, so the token never reaches a row, a log line or an error), keeps `app_id` in the record because it is not a secret, and puts `app_secret` only in `secrets.json`; a half-saved pair is `missing` and dials nothing. The record also carries the guest list the inbound gate reads — `allowed: [{ openId, name? }]`, nobody by default, changed only through `connector-allow` / `connector-block` (both `SHARED_BLOCKED` like the rest of the `connector-*` writes, both routed in `channel.js`), so a stranger's message starts no turn and appears on the row as one refused sender. `Disconnect` closes the socket and clears both credentials. `feishu` joins `github` and `composio` in `RESERVED_NAMES`, so a saved capability cannot take the row's id.

### Secret scope defaults (#545)

A key the owner saves is for **all of the owner's Bots** (`scope: 'all'`) unless the owner narrows it: a card's "Only <Bot>", the Secrets page's *Chosen Bots* or *No Bot*. That holds for a connector key too (`GITHUB_TOKEN`, `COMPOSIO_API_KEY`): `connector-connect` no longer passes `scope: []`, and a reconnect keeps the scope the key already has. A scope the owner chose is stored with `scopeSet: true` (`secret-update`, `secret-set` with a `scope`, a card's "Only <Bot>", and a deleted Bot leaving a picked list), so an empty list stays "No Bot". On load, an empty list **without** `scopeSet` is the old connector default and becomes `'all'` once (written back by the host that holds the team; a reading host widens it in memory only). An empty list the owner picked before #545 carries no marker and is widened too: there is no way to tell it apart. **Every turn of every one of the owner's own Bots** gets the keys its scope allows (owner decision 2026-10-22, #601: 「放开这个权限管理，我的bot都应该能看到」). Where the turn came from no longer matters for secrets: a group round, a Bot-to-Bot relay, a scheduled turn, a turn a friend started on a shared Bot, a turn with no recorded origin, and bash inside a sub-agent all get them. A sub-agent's shell resolves to its parent Bot along the same chain as the connector guard (`rt.whoseAgent`, from `connector-access.js`); a chain that cannot be followed to a Bot gets no value. The boundaries that stay: a friend's Bot (`remote`) never gets the owner's keys, and a key scoped to chosen Bots goes only to those Bots. A capability (`canUseSecret`) follows the same rule. This replaces the turn-origin rule of #545/#581, under which a shell got `'all'` keys only on a turn that `settled` as the owner's. The connector *tools* follow the same rule (#601, below); secrets no longer read `turn-origin.js`. Owner decision 2026-10-20 (#359, AGENTS.md hard rule 4).

### A withheld key says why (#651)

A key that is not in a shell used to look exactly like a key the owner never saved: `resolveEnv` returned `{}` and the Bot reported "no key configured". `resolveEnv` writes `DSH_SECRETS_WITHHELD` — a comma-separated `NAME:reason` list, never a value — with one reason from a closed set. Since #601 only the real boundaries are left: `remote-bot` (a friend's Bot), `not-in-scope` (the owner scoped the key to other Bots, or to none) and `unknown-bot` (a sub-agent whose parent chain cannot be followed to a Bot). The per-turn reasons of #651 (`turn-not-owner`, `shared-bot-scheduled`, `shared-room`, `unknown-turn`) are gone with the rule they explained. A Session of no Bot (the DSH Agent) gets `{}` as before. `list_secrets` and `request_secret` say "you may use it" for every key in the Bot's scope, and that a friend's Bot never gets one. `DSH_SECRETS_WITHHELD` is declared in the `ds-bot-secrets` shell-env contribution next to the `DSH_SECRET_*` keys: DSH's `ShellEnvRegistry.collect` throws on a key a contributor did not declare, which would fail the whole bash call. The test bench's `env()` enforces that same contract. Tests: the `#601` and `#651` cases in `core/test/secrets.test.js`.

### Per-Bot connector access (#335, #369, #601)

The connector tools are mounted once for the whole DSH profile, so which Bot may use them is decided in `src/host/connector-access.js`.

**Decision (the owner, 2026-10-22, #601: 「放开，主要应该用连接器工具」; it supersedes #369's "off by default for other people's use"; one exception, #1237, is the group room's composio and schedule tools, below).** Every turn of every one of the owner's own Bots may use the connected connectors, whatever started it: the owner, a group round of any origin (also a room with a friend or another person in it), a Bot-to-Bot relay, a scheduled turn, a friend talking to a shared Bot, a turn with no recorded origin. The connector tools no longer read `turn-origin.js`.

- **Per-Bot record** (only what differs from the default is stored): `bot.connectors = { github?: false, composio?: false }` is an explicit off for that Bot (absent = on; a legacy `true` from #346 reads as on). `bot-connectors { botId, connector, enabled }` writes it; a `scope` an older client still sends is ignored. The retired "also when others use it" offer (`bot.connectorsShared`) means nothing any more and is dropped on the Bot's next switch or on a disconnect.
- **A run Bot started by a friend's Bot reaches no connector (#1555).** `run_workflow` and `define_workflow` have no `visibleTo`, so a friend's Bot can call them; the run Bot names that remote Bot among its caps (`cappedBy`; a record written before #1582 named it in `createdBy`), which has no switch table of ours to intersect with. The ephemeral branch reads that as "every connector switched off": `allowed()` requires the step tools to name the connector **and** a caller that is not remote, so the guard refuses with `The github connector is not available to a run started by a friend's Bot.` and the same `denied()` takes the connectors out of the run Bot's tool list. A run with no cap (the owner, the board, an older run) and a cap that names a Bot the team no longer has keep the answer they had, and an in-team caller whose own switch is on, whose node names the connector, still gets it. `visibleTo` on the two tools stays backlog.
- **Boundaries that stay.** A friend's Bot (`bot.remote`) never gets the tools. An Agent whose Bot cannot be determined (a parent Session that is gone, or a parent chain deeper than eight) gets none either (fail closed), so an unresolved sub-agent never reads as a plain owner Session. A chain that really ends at a Session of no Bot (the DSH Agent, a plain Session) keeps them. A sub-agent Session is followed to its parent Bot (`whoseAgent`, also on `rt.whoseAgent` for `secrets.js`).
- **Enforcement is two layers.** A `ctx.tools.guard` refuses every `mcp__github__*` / `mcp__composio__*` call that is not allowed, and `agent.ctx.tools.restrict({ deny })` takes the same tools out of that Agent's tool list. The mask is refreshed when the Agent is created, on every `resolveAgent` (delivery), when a switch changes, and on `tools/change` (a connector that mounts or goes away later). Turns and sharing no longer change it. DSH's hidden "Tool added/removed" notices for these tools are not drawn in the chat (`cells.js`).
- **A mask that cannot be rebuilt keeps the previous one (#1271).** `hideConnectorTools` lifts the old mask before it reads `schemas()` again, so a `restrict()` that refuses a name would otherwise leave the Agent with no mask and every tool listed again. The rebuild now names only what the global view (`schemas()` with no Agent) can restrict, and if a restriction still fails the catch puts the previous deny list back: the guard refuses a call either way, and a list that widens by itself is a wrong answer. A denied name the Agent itself serves stays listed — `restrict()` cannot name a scope's own tool — and the warn line says so.
- **A group room turn carries no composio tools and no schedule tools (#1237).** The eight tools — `mcp__composio__*` and `schedule_create` / `schedule_list` / `schedule_update` / `schedule_delete` — are 20,355 characters of schema (≈5.2k tokens at the measured 3.92 chars/token) on every call, and a room round uses neither: an outside app is reached from the Bot's own chat, and a schedule belongs to a Session (#628), so managing it from a member's room Session would write to the wrong place. The rule is one function in `connector-access.js`: the same `denied()` that answers the per-Bot switches also names these eight when `rt.groupOwners` — the store's Session → room index — has the Agent's Session, so the mask rides the existing refresh points (Agent created, `resolveAgent` on every delivery, a switch, `tools/change` for a plugin that mounts later) and the guard refuses a call with `… not available in a group room` — the room answer comes before the friend's-Bot one, and a friend's Bot has no composio tools in its own chat either, so the refusal does not send it there. A room still reads GitHub: judging a pull request is what a room round does, so its read tools stay.
- **A group room keeps github's read half only (#1234, the first step of #1237's 「不做」).** The 43 github tools were 47,413 characters of schema on every call of every room turn (#796: `request/header` 115,020 → ~47,300 characters once the writes go, ≈12.1k tokens a call). A room round reads a pull request and never creates, merges or pushes one — a Bot that means to change GitHub does it from its own chat — so the rule is a whitelist on the same `roomHidden()` the composio rule uses: under `mcp__github__` only `list_*`, `get_*` and `search_*` stay, and every other name (create/update/delete/merge/push/comment/…, and a new tool nobody classified) is dropped from that Session's list and refused by the guard. The refusal **names the tool** — `The mcp__github__create_pull_request tool is not available in a group room (#1234): a room gets GitHub's read tools (list/get/search) only. Change GitHub from your own chat.` — because a silent disappearance reads as a broken tool. Composio and the schedule tools keep their #1237 sentences, the Bot's own chat, its earlier parts and its sub-agents outside a room are unchanged, and `core/test/connector-access.test.js` pins each family: the reads stay, each write leaves, an unclassified tool fails closed, a chat Session is untouched, and the room's list is the chat's minus exactly the hidden names.
- **Bots prefer the connector for GitHub.** The Bot rules (`prompt.js`) say to use the GitHub connector tools first and `$DSH_SECRET_GITHUB_TOKEN` with `gh` or `git` in the shell only for what they cannot do, such as `git push`.
- **Defaults and disconnect.** New and duplicated Bots (and tree children) start on. The Connectors row reads "On for all N Bots", "On for K of N Bots" or "Off for every Bot"; **Choose Bots** and each Bot's **Connectors** card show one switch per Bot and connector. **Disconnect** clears every Bot's record for that connector. The switches change only through the `bot-connectors` channel endpoint, which Bots do not call; it is in `SHARED_BLOCKED`, so with more than one member it is refused like the other connector writes.
- **Whose request a turn answers** (`turn-origin.js`, recorded by `turns.js`, carried by relays, posts and resume records) is still tracked: standing approvals (`approvals.js`) and resumed turns read it. It no longer decides connector tools or secrets.
- **Not covered here:** a per-app choice per Bot (the Composio app list is still one list for the connection), and DSH's own tool approval, which still decides which allowed tool runs without asking.

### About FlyBot data: repository, build and update text (#374)

The About page's facts come from `src/host/update.js` and the core's `package.json`, which now name **ThinkFlowLab/FlyBot** (`repository.url`, `directory: "core"`, `homepage`, `bugs`), not the upstream DS Bot: `repoSlug()` feeds the Star button and its live count (`repo-stars`, hidden when the answer fails), **Source code**, **Release notes** (`<repo>/releases`) and the DSH-update check, and `ISSUES_URL` in `diagnostics.js` is `ThinkFlowLab/FlyBot/issues/new` (its `bug.yml` has the `what` and `diagnostics` fields the Feedback page fills). The DSH-update check reads the latest FlyBot release's `core/package.json` for a `dsBot.verifiedDsh` declaration; none is declared today, so no DSH update is offered, which matches the README's pinned DSH version.

- **Build of a git install.** `sourceOf` gives a non-version ref as `branch` (`github:ThinkFlowLab/FlyBot#main&path:/core` → `main`), and a **40-hex ref as `commit`** (`#<sha40>`: pinned, no branch, no tag; a shorter hex run stays a branch name, #379). `commitOf` takes the commit from, in order: the spec's own pinned hash; the profile's `pnpm-lock.yaml` (`lockedCommit`: the `ds-bot@…/tar.gz/<sha40>` entry of **this package only**, so the social/tree plugins from the same repository never answer for it, and two different commits for it give none; a DSH profile is hoisted, so the real path is plain `node_modules/ds-bot` and holds no commit); then `installedCommit`, the 40-hex commit that follows (or precedes) the repository name in the running package's **real path** (the isolated pnpm layout). No match means no commit is shown, never a guess. The view carries `build: { branch?, commit?, pinned? }` (commit is the short 7; `pinned` when the spec names the commit) for git installs and `null` otherwise. The lockfile format was checked against a real `pnpm add` into a hoisted profile.
- **How far behind.** For a branch install with a known commit (a pinned commit has no branch, so nothing is compared), a check makes one unauthenticated `GET /repos/<owner>/<repo>/compare/<commit>...<branch>` and reports `behind` = `ahead_by` only when the answer's `status` is `ahead` or `identical` (null on a failure, a `diverged` branch, a branch reset or force-pushed to before the commit (`behind`), or a branch name with odd characters), so a commit that is no longer on the branch never reads "Up to date". Nothing is ever offered to install for a branch install: updates come from the maintainer reinstalling FlyBot. `config.packagePath` overrides the path read, for tests.
- **Version.** `current` is still the core's own version (`0.1.5-flybot.1`); the page adds `· <branch> <commit>` to it. FlyBot's product version (tags such as v0.1.0) is not in the install, so it is not shown.

### Automation tasks on by default (#378)

DSH 0.2 offers the schedule service only through its optional bundle `@deepseek-ai/dsh-experimental-schedule-bundle` ("Automation tasks"), and the bundle list in a profile belongs to DSH. Without the bundle `schedules.js` has no service and Settings → Scheduled tasks shows only the hint. The bundle ships inside the DSH install, so the core adds no dependency (`core/package.json` is unchanged).

- **How.** About 20 seconds after start, `automation-default.js` calls `pluginManager.listBundles()` and, for a profile that has not been offered yet, `setBundleEnabled(bundle, true)`: the same call the Plugins page makes, applied live. It does not write the profile's manifest or patch files itself. A static `cordis.patch.yml` insert was rejected: the Plugins page could not turn it off and it would duplicate the rows of anyone who already switched the bundle on.
- **Once per profile.** The offer is written first to `dsh-defaults.json` in the team's home (`offers[<bundle>][<profile name>]`), then made. A bundle that is already on is noted the same way. After that the profile decides, so a person who switches Automation tasks off keeps it off across restarts and updates.
- **Fail closed.** An unreadable record, a record that cannot be written, a DSH without the bundle or without a plugin manager, a bundle with a load error, and a window that only shows the team (`rt.readOnly()`) change nothing. A refusal by the manager withdraws the note so the next start tries again.
- **Opt out.** `automationTasks: false` in the `bot` config.

### Scheduled tasks: the Bot-wide list (#628)

DSH's own `schedule_list` answers for the Session the call runs in, and its `[]` is indistinguishable from "this Bot has nothing scheduled": a task the owner sees in the UI is invisible from another Session of the same Bot. On 2026-10-21 that produced a written claim that a live schedule had never existed, and it came close to a Bot "cleaning up" a timer it could not see.

- **`bot_schedules`** (no arguments) answers for the calling Bot. It reads the host-wide `catalog()` and keeps the Sessions that speak for it: its own chat (`chatOwners`), the archived parts of it (`pastOwners` with no `roomId`), its group Sessions, live and archived (`groupOwners` / `pastOwners` with a `roomId`, named by the group chat), and a **group chat's own Session** — the group's tasks live on the room's Session id, kept when the calling Bot is in `room.members`, so every member (the admin too) sees them and a Bot outside the group does not. Its paused tasks come from `state.pausedSchedules`, including those on the group's own Session. Each line carries the id, the title, the next run, the state and the owning Session; the answer says in so many words that it is Bot-wide and that `schedule_list` is per Session, so an empty answer cannot be read as a claim about another Session.
- **Read-only, and it changes nothing about the scoping of the rest.** `schedule_create` / `schedule_update` / `schedule_delete` and DSH's own tools keep their session rule; the tool adds a way to *see* the Bot's tasks, not a way to edit them without knowing the Session.
- Tests: `core/test/schedules.test.js` (`#628: bot_schedules answers for the Bot…`, the group-chat-own-Session cases, and the service-off and empty-list cases).

### Scheduled tasks: edit, pause, missed runs (#354)

- **Edit** (`schedule-update`). On the same Session an active task goes through DSH's compare-and-update with the exact record `list` returned, so its id, next run and delivery records stay; the timing is sent only when it changed, so renaming a task does not move its next run. Moved to another Bot or group chat, or a finished one-time task, the new task is created first and the old one deleted after, so a failure keeps the old task (a part move needs no such create — it rewrites the stored row, below). `when: { kind: 'keep' }` keeps the timing (a cron rule the form cannot show). The edit needs the task's Session **and** its new target (`authz.js`), its text gets the same chip check as `schedule-create`, and its source must belong to the caller's own user (#1321, the rule in **Scheduled tasks: copy**) — authz admits a room's current member, so that last check lives in the data layer.
- **Part move** (`moveSchedules`, #1245). A handoff is not an edit, so the earlier part's active tasks are **rewritten in place** in DSH's storage domain, inside `service.serialize`: the row keeps its id, record and delivery history and only `sessionId` changes to the fresh Session. The next run therefore stays the instant it was already due — creating the task again would set `now + interval` (the slip and reset history #1245 documents) — and a one-shot whose time has passed stays where it is. The due set is unchanged, so the runtime needs no re-arm: it re-reads the table before every delivery. A failed write leaves the task on the earlier part, with nothing half-deleted, which is the property #901 relies on. The write reaches DSH's storage domain directly — `getDomain()`, `serialize()`, `table('tasks')`, `put` and the `tasks` row shape are **private** in `@deepseek-ai/dsh-schedule@0.2.0-rc.2`, so re-check them on every DSH upgrade. A missing or renamed `getDomain()`, `serialize()` or `table('tasks')` throws before the loop: nothing moves and `moveSchedules` warns `ds-bot: tasks of %s not moved`. A missing or renamed `record` throws inside the loop, on the first row that passes the filter, so rows already written in that call stay moved — a uniform drift moves nothing, a partial one leaves it half done (the same `ds-bot: tasks of %s not moved` warn fires). A missing or renamed `put` throws per row: the per-row catch warns `ds-bot: task %s stayed with the earlier part`, and only that row stays behind while the loop continues. A renamed row field the filter reads (`sessionId`, `status`) throws nothing and warns nothing — every row is skipped silently, so a fake row carrying `state` instead of `status` is skipped and grepping either warning finds nothing, and those tasks silently stop firing rather than crash. A present `record` with a renamed `kind` reads as `kind: undefined`, so the one-shot test is false and an expired one-shot is moved to the fresh part; a renamed `scheduledAt` reads as undefined, so `Date.parse` gives NaN and the expiry check passes — those rows do not stop firing, they move and can fire there, an expired one-shot late. The tests model the same private shape, so they will not catch any of it.
- **Pause / Resume** (`schedule-pause`, `schedule-resume`). DSH has no pause (its README: "Pause ... not supported"). Pause writes the task's record to `state.pausedSchedules[<id>]` (`{ id, sessionId, record, pausedAt }`) and saves the team before DSH deletes the task; a failed delete takes the entry back out, so the task keeps running. Resume creates the task again on the Bot's current part (or the group's Session) before the entry goes, so a failed create leaves it paused. A paused task lists with `status: 'paused'` and its id, can be edited (it stays paused) or deleted, and a one-time task whose time passed while paused is refused until it is edited. A recurring task's next run is computed afresh on Resume.
- **Missed runs** (DSH's behavior, checked against the pinned `@deepseek-ai/dsh-schedule`). Tasks are stored by the host and survive a restart, but run only while the app is running. After the app was closed, a recurring task (every N minutes, daily, weekly, cron) runs **once**, for its latest missed time, and then waits for its next future time: it never runs once per missed time. A one-time task whose time passed while the app was closed runs once when the app starts again. A paused task runs no missed time at all. DSH notes one exception it does not rule out: a crash or shutdown between delivering a reminder and saving that it did can deliver that one reminder again. Test: `a recurring task missed while the app was closed runs once, for its latest time` in `core/test/schedules.test.js`.

### Scheduled tasks: copy (#1287)

A task can be copied to another Bot or group chat: the same title, prompt and timing, on the target's current part (a Bot's current chat, an earlier part's task included anyway), keeping the source's **next run**. `schedule-create` takes `copyFrom: { sessionId, id }` — no second endpoint — and the source is resolved through the same ownership check `schedule-update` uses, or from `state.pausedSchedules` when it is paused.

- **A new row, not `create`.** An active source is read in DSH's storage domain and written back as a new row inside `service.serialize`: a fresh id in DSH's own shape (`schedule-<uuid>`, retried on collision rather than overwriting), the source's record under it, `status: 'active'`, and an **empty** `deliveryHistory` with no `lastDelivery`. Copying through `create` would anchor an `every` task to `now + interval` — #1245 with a new name — and would carry the source's delivery record, which `checkMissed` reads as "this run was already delivered", so the copy would never fire. The private API is the one **Part move** already documents (`getDomain()`, `serialize()`, `table('tasks')`, `get`, `put`, the row shape), so re-check it on every DSH upgrade; this path sits outside the `moveSchedules` warn-and-continue loop, so a renamed `put` or `get` rejects the copy and writes nothing.
- **No re-arm.** The copy's due instant is the source's, and the source's own row keeps it in the driver's global minimum, so the row is covered before it exists.
- **A paused source** has no next run to keep, so its copy goes through `create` with the stored record's timing, as Resume does. A one-time task whose time has passed is refused with `Pick a time in the future`, the same sentence Edit uses, because such a copy could never run.
- **Refusals.** An unknown source Session, an unknown id, the same Bot or group chat as the source, and an unknown target each get their own sentence; a copy to the same chat never falls through to `No such task`. Quiet hours are checked as on create (a repeat or cron rule is let through, as the view says).
- **Same user only (#1321).** The source is the caller's to read only while it belongs to the caller's own user. `copySchedule` and `updateSchedule` resolve it through one `sourceOf(sessionId, actor)`, and where `authzEnforced()` is true an owner that is not the actor's answers exactly as an unknown source does — the existing `No such task`, no second sentence and nothing about the other member's task. Ownership here is the Bot's `ownerId`, or `rt.roomOwnedBy` for a room's own Session (every member Bot belongs to that user); it is deliberately **not** `rt.sessionOwnedBy`, which also admits a room's current human member, so being seated in a room is not owning its task and a shared room's task is nobody's single user's. The actor reaches the data layer as `scheduleEndpoint(endpoint, body, actor)` from the channel, because authz cannot see a `copyFrom` or an edit's source. A deployment with nobody signed in is untouched: the legacy single-human path still copies across Bots.
- **Tests:** four in `core/test/schedules.test.js` — the copy's id, next run, empty history and untouched source; the four refusals; a daily rule's time and zone plus an earlier part's task going to the target's current part; and the five owner-scope cases of #1321 (a peer's task refused by copy and by edit; a refusal that writes nothing and carries nothing of the source; the owner's own copy still landing; and the unsigned single-human copy still allowed).

### Scheduled tasks: team quiet hours (#1166)

A window that a **new or edited** task must fall outside — not a mute. The window itself is a wall clock, but the time a task would be due is read in **that task's own zone** (the next bullet), so the two are compared as instants rather than in one team-wide clock. `state.prefs.quietHours` holds `{ on, from, to }` beside the other team preferences, and its absence or `on: false` is off, which is the default (`src/shared/quiet-hours.js`, and `setPrefs` in `channel.js`).

- **Checked once, at the create/edit moment.** `schedule-create` (a copy through `copyFrom` included, #1287) and `schedule-update` refuse before any `service.create` / `service.update` / `service.delete`, with the named code `bot/quiet-hours` and a sentence naming when the window ends, so the form's existing error line shows it and nothing is created or moved. `when: { kind: keep }` changes no time and is never checked. The window is half-open `[from, to)` — `from` refuses, `to` allows — and a window whose end is earlier than its start crosses midnight.
- **What the clock is.** A one-shot `at` is an instant, read in the zone the form sends with the timing (the browser's), falling back to the host's when that zone is unreadable. `daily` and `weekly` carry their wall clock and zone with the time itself, so the check reads the clock as written.
- **`every` and `cron` are allowed, and said so.** DSH computes a repeat rule's next fire and `catalog()` answers only for a stored task, so FlyBot cannot check one without duplicating DSH's scheduler. The view carries `quietUnchecked: true` while quiet hours are on and such a task exists, and that flag is the **only** place the rule is computed: the page renders it as one line and does not scan the task list itself (`core/src/client/schedules.js`), so a repeat task deleted between two polls cannot leave the line behind, and a line cannot appear without the host's claim. Visible, never a silent claim of silence.
- **Nothing existing is touched.** A task that already fires inside the window keeps firing, and turning quiet hours on makes no `update` or `delete` call. The suppression half — muting a delivery and recording it, with a count on the team view — is **not implemented**: DSH has no pre-delivery veto and no `pause` (`ScheduleService` has `create`, `list`, `catalog`, `history`, `delete`, `update`), so it waits for a hook (#1166, tracked as blocked-on-DSH).
- **Not on other paths.** Direct messages, @-mentions and approval requests are untouched: the change reaches no turn or notify code.
- **Tests:** `core/test/quiet-hours.test.js` — the window and the zone reading, a refusal with no service write, the end minute allowed, a refused edit that leaves the task as it was, the two allowed rule kinds and their marker, an existing task left alone, and the settings write refusing an invalid window.

### Scheduled tasks: last run and Retry (#473)

DSH's catalog carries `lastDelivery`, an inbox receipt (the reminder reached the Session), not how the Bot's turn went. FlyBot records each task's last run in `state.scheduleRuns[<id>]` (`{ at, result, reason?, messageId?, missed? }`, the newest 200 tasks), saved with the team.

- **A run.** `turns.js` hands every `user/message` whose source is `schedule` to `rt.scheduleRunStarted`, which reads the task ids from DSH's framing (`schedule_id_json`, or each `reminders_json` entry of a batch) and records `running`. The turn's `turn/end` settles it (`rt.scheduleRunEnded`): `failed` with the turn's error line when the turn errored, `stopped` when the user stopped it, `ran` otherwise. A group task's run is the group Session's turn; it fails when a member's turn in that round failed (`rt.scheduleRoundFailed`, from `group_relay`).
- **What counts as failed** (Owner decision 2026-10-20): DSH could not deliver the reminder, or the Bot's turn errored. A turn that ends without an answer has run.
- **Not delivered.** DSH logs a delivery it could not make and does not retry it by itself (its runtime: "refused admission does not retry automatically"), so the task stays active with its time in the past. A check every minute (and on each `schedules` read) notes such a task the first time it sees it and calls it failed ("DSH could not deliver it") when it is still due 2 minutes later, once per missed time. Seeing it due once is not enough: right after the app starts, DSH is still delivering the times it missed while closed.
- **The row.** `schedules` adds `lastRun: { at, result, reason? }` to each task: FlyBot's record, or `delivered` when DSH's `lastDelivery` is a newer message than the record (the Bot has not taken it up yet).
- **Retry** (`schedule-retry`, `{ sessionId, id }`, the same ownership check as Pause). It sends the task's prompt once now to the Bot's current part (or the group's Session) as a `schedule`-source message in DSH's reminder framing, so the turn is that task's run, a group gets its prompt (`reminderText`), and the connector verdict is the scheduled one (`turn-origin.js`). DSH's own times are untouched: no missed time is delivered again. A paused task is refused ("Resume the task first").
- **Needs you.** A failed turn of a scheduled run is already one of the ended turns (`work.ended`) that the finish/fail notifications read (#353). A reminder DSH did not deliver ran no turn, so `schedules.js` adds it there itself (`rt.noteRunFailure`, `failed: Scheduled task "<name>" was not delivered`), with the same exclusions (a friend's Bot, a room shared with other people). The Agent inbox reads failed ended turns from that same list (#471); no second event path.
- **Limits** (#56) are not part of this step.
- Tests: `core/test/schedules.test.js` (`a run fails only when its turn errors…`, `Retry runs the same prompt once now…`, `a due task DSH does not deliver…`).

### State journal (#511, opt-in)

A local, replayable record of every change to the saved team, for multi-Bot bugs that reproduce only sometimes. Owner decision 2026-10-20 (option a): state mutations only (decisions stay in #396), off by default, 7 days or 20 MB, dev-only replay, local only.

- **On.** `stateJournal: true` in the `bot` config. Off (the default) nothing is opened or written, so every other test runs as before.
- **What.** `src/host/journal.js`. After each successful `state.json` write, `store.js` hands the exact snapshot text to the journal, which appends the difference from the last recorded snapshot to `<home>/journal/state.jsonl` (file mode 0600, folder 0700). Lines are `{ seq, t, op, key, prev, next, botId?, actor }`; `op` is `base` (the whole team: the first line, and any change only a key reorder explains), `set`, `delete`, or `append` (`prevLength`, `drop`, the new items: a group log or other list that grew or slid). Paths go at most three keys deep (`bots.<id>.<field>`); `botId` is set on a `bots.<id>` path; `actor` is `host` for a save and `retention` for a folded base (per-call attribution is not recorded). Only the host that holds the state lock writes, so a read-only window records nothing.
- **Retention.** When a write would pass 20 MB, or the oldest change is older than 7 days, the oldest lines are dropped down to 90% of each cap and folded into the base line (atomic rewrite), so the kept lines still replay. A team that alone exceeds the cap stops recording.
- **Fail closed.** Replay (`replayTo(text, seq)`) refuses the whole journal on an unreadable or incomplete line, an unknown op, a gap in `seq`, a first line that is not a base, or a `prev` that does not match what the earlier lines built; a `seq` outside the file is refused, not approximated. On start the writer replays the existing file the same way; a journal that does not replay, a path that is not a plain file, or a failed write stops recording for that run with a warning and leaves the file as it is. Saving the team never depends on the journal.
- **Replay.** `core/scripts/replay.mjs` (dev-only, not in the package, see [install](install.md)) prints or writes (`--out`, new file only, 0600) the team after a given `--to <seq>`; it makes no network or process calls. Test: `core/test/state-journal.test.js` (a 3-Bot round replays byte-identical at every step).

### Standing tool approvals (#540)

DSH's approval outcomes are one-shot (`ApprovalOutcome`: `allowed-once` / `rejected` / `cancelled` / `unavailable`; `ApprovalPolicy` is `ask` / `never`), so a permanent approval lives in FlyBot, not in DSH (no DSH patch). `src/host/approvals.js` keys a request by its kind (`approvalKind`: the tool, plus the sandbox mode when DSH's reason reads `escalate sandbox to <mode>:`, e.g. `bash:escalate:danger-full-access`). `approval-answer` takes `always-bot` (kept on the Bot as `standingApprovals: [{ kind, label, at, ownerId? }]`) and `always-room` (kept on the room the ask came from; refused for an own-chat ask); both save, answer this ask `allowed-once` and release other waiting asks the grant covers. The `approval/request` listener answers `allowed-once` itself, before any card, only for a turn the owner started (`settled(...) === 'owner'` from `turn-origin.js`; a friend's message, another member's line or a room with other people in it still asks), or for a turn that carries **no verdict at all in the Bot's own chat** — DSH starts such a turn for its own retry after the owner answered, and nobody's request is in it (#608) — and only when the Bot (a local one, never `bot.remote`) has the kind, or the ask comes from a group Session of a room holding the kind for the Bot's owner (`ownerId` matches while authz is enforced; before anyone signs in every local Bot is the one person's); a group grant does not cover the Bot's own chat. DSH's audit pair (`approval/asked` / `approval/decided`) still logs each auto-answered ask. A grant that a turn cannot use is not skipped silently: the first such ask per Session and kind logs `the standing approval for <kind> was not used: the turn is "<verdict>"`. `standing-approval-remove { scope: 'bot' | 'room', id, kind }` revokes (a signed-in remover takes only their own group grant). Authz: an `always-*` answer needs the Bot's owner (owning the room is enough only for Allow once); removing a Bot's grant needs the Bot's owner, a group's the member who gave it. Tests: `core/test/group-status.test.js`, `core/test/authz.test.js`.

### Discarded promise `.catch` (#213)

A discarded `.catch(() => {})` in the host sources either starts with `void` (fire and forget) or carries a one-line reason comment (an awaited wait); a `.catch(() => undefined)` whose value is used stays. `check-empty-catch` enforces it (see `docs/code-standards.md`).

### Images a text-only model cannot see (#779)

`src/host/images.js` reads a chat image with a model that declares image input before the request reaches a model that cannot (`ocrRoute`: `config.ocrModel` first, then served models declaring `image`, the DSH default first among them; `config.textOnlyModels` names a model whose provider claims image input but rejects it). Readings are cached per attachment in `<home>/ocr.json`, so later requests repeat the same words and the prompt cache still hits.

- When no model can read an image, both places it becomes text — a Bot chat (`imageAsText` through `withImagesAsText`) and the group relay (`imagesForGroup`) — use the same `imagePlaceholder`.
- That placeholder names the file when the Bot's own file tools can open it: `attachmentFilePath` takes the attachment store's `imageHostPath` through the file sandbox's `processPathFromHostPath` (the same mapping `dsh-spill-policy` applies to spooled tool output) and falls back to the local object layout `<home>/attachments/v1/objects/<first two>/<sha256>`. Either candidate must `stat` as a regular file, so a Bot is never sent after a file that is not there (a host path the sandbox cannot open is worse than no path), and only a `sha256:<64 hex>` id has an object path at all.
- Nothing is copied into a Bot's working folder: a copy would need a lifecycle and a cleanup policy of its own, and the readable path already lets a Bot move or submit the bytes itself.
- Covered by `core/test/images.test.js` and, through the Session hook and the group relay, `core/test/session-identity.test.js`.

### The Project board and who may act on it (#1710)

`projectEndpoint` takes the authenticated actor. `project-create` stamps the caller's member id as
`ownerUserId` (an `ownerUserId` in the body cannot mint a Project someone else manages); an install
with no signed-in session falls back to the first member, the same rule `tasks.js` uses for
`requesterOf`. `project-read` answers `{ project, canManage }`, where `canManage` is true only for
the owner — or for every caller on a Project whose record names no owner. `project-bind` is refused
by the host with `bot/forbidden` unless the caller may manage the Project the binding names (or the
one it is leaving, when unbinding); the refusal writes nothing, so hiding a button is never the
gate. Reading the board (`project-board`) stays open to a non-owner: the same rows, read-only.
Those rows are the ones the caller could open through `tasks` (#1723): `store.js` passes the
authenticated actor into `projectBoard(projectId, actor)`, and the board drops every card
`rt.taskVisible` refuses — a card is visible to its requester, to the owner of its Bot or an
ancestor of it, and to the admin of the room it came from. The predicate stays in `tasks.js`, one
copy of the rule `tasks` itself answers with, so the board cannot paint a card the same member is
refused there; a board with nothing to paint is still `[]`, not an error.
`project-board` is listed in `authz.js`'s `TASK_ENDPOINTS`, so a signed-in deployment does not
refuse it as an unknown endpoint.

### Role queues, isolated workers and lease recovery (#1729)

Stage 3.2 of the task pool. One queue per role, one worker per claim, one owner for an expired lease; all of it reads the cards already on the board, so there is no second store.

- **Per-role cap.** `ROLE_QUEUE_CAP` (8) is the default ceiling for one role's queue in one group. A graph states its own through `cap` on the enqueued item, kept on the card as `queueCap`; a re-offer keeps the card's id and is never counted against itself. An enqueue over the ceiling is refused `queue-full` with a sentence naming the role and the cap (`the Dev queue already holds 8 items, its cap is 8`), so the caller knows which queue is full rather than seeing a silent null.
- **Isolated workers.** A claim creates a worker (`worker-<hex>`, kept in `tasks.js`'s own map, capped at 64, oldest dropped), and the card names it in `worker`. `rt.taskWorkerState(id)` is the only read: an unknown id answers `undefined`, so a second claim cannot see the first's `files` or `vars`. `requeue` and an expired lease drop the worker, so the next claim starts clean.
- **One owner for an expired lease.** `expireLeases` reads the lease once, clears it, then returns a queued card to its role queue — a second read in the same tick finds no lease and answers 0. The recovery is written to the card's `evidence` (`lease expired (held by <name>)`) within the existing eight-entry cap, the dead worker is dropped, and a card that is not a queued item only loses the dead lease. A live lease is untouched, so a restart with a live lease is a no-op; a claim on a live lease is refused `lease-held` naming the holder. `rt.taskExpireLeases` exposes the same read, and `rt.taskLease(id)` gives `{ holder, takenAt, expiresAt, live, heldBy }`; the workflow plugin reads the lease through `fb.tasks.lease(id)` and never keeps a copy.
- **Measured deliveries.** `rt.taskCounters({ role?, run? })` counts `queued`, `claimed`, `working`, `blocked`, `accepted`, `failed`, `cancelled` per role and per run id from the rows, plus `deliveries` and `workerSeconds` (accepted cards with a lease, measured from `takenAt` to the card's last update). A rework chain is one accepted delivery (#1730): an accepted `rework` child whose `reworkOf` parent is also accepted folds into the parent's delivery, so a rejection→rework→accept cycle is two records and one delivery; a child whose parent never landed stays a delivery of its own, and a replay writes no rows so the count cannot double. `fb.tasks.counters(query)` is the plugin seam. No metric store is added.

**Audit projection (#1730).** `rt.taskAudit(id)` renders one text block from the typed fields already on the card — `handoff` from→to/reason/at, each `evidence` entry (sha, pr, check, at), the `reworkOf` chain oldest→newest, and the current lease holder with its `takenAt`→`expiresAt` window. It is a read: nothing is written, minted or cached, so the same rows render the same text twice. A record stored before the slice carries none of the fields and answers the empty string, not a throw. The Project board puts the same text on its row as `audit` (only when non-empty) and the client shows it inside the existing card detail — no new endpoint and no new page. Tests: `core/test/task-audit.test.js`.
- Tests: `core/test/task-queue-lease.test.js` — the cap refusal names role and cap, a re-offer keeps its id, two concurrent claims share no worker state, two expired reads requeue once and record the holder, a live lease refuses a claim naming the holder, a restart with a live lease changes nothing, and the counters read from the rows.

### Meetings: a decision with a lifecycle (#1731)

Stage 4.1 gives an unresolved conflict a record instead of a chat. `core/src/host/meetings.js`
keeps meetings in the existing store (`state.meetings`) and registers one `meeting` tool; there is
no second store, no UI-only path and no cron.

- **Lifecycle.** `open → deliberating → decided | blocked`, bound to one question and, when there is
  one, the issue and Project that triggered it. Recording the first position moves `open` to
  `deliberating`. At most one meeting per question may be open or deliberating: a second one is
  refused `duplicate`, comparing the question with casing and whitespace flattened.
- **Positions.** An invited participant records `agree`, `dissent` or `abstain` with a line of text.
  A name that was not invited is refused `not-invited`; a dissent with text is also kept as the
  meeting's standing dissent, owned by the participant who recorded it. A participant who never
  answers and is not recorded `silent` keeps the meeting from closing.
- **The governance check is code.** `governanceRefusal(meeting)` is the one refusal `decide` runs
  before it writes anything: every invited participant has a position or is recorded silent, the
  decision names an `owner`, a dissent carries its own `owner`, and the decision states what was
  decided. It answers the reason, or `undefined` when the meeting may close. `blocked` needs one
  one-sentence blocking question, writes no decision file and produces no task.
- **Archived decision.** `decided` writes exactly one `decisions/<YYYY-MM-DD>-<slug>.md` (Stage 1
  shape: Date, Decision, Class, Evidence, Participants, Dissent, Status, Links, `Written-by:`), in
  the Session's working folder, and refuses `exists` rather than rewriting an earlier conclusion.
  The meeting keeps the file path and its sha256; every evidence `sha`/`pr`/`check` and every
  participant name is in the file's text.
- **Linked tasks.** Follow-up cards go through `rt.taskEndpoint('task-create', …)` — the one task
  write path — as `taskClass: 'work'`, each carrying the decision file path in its `evidence`. A
  meeting never keeps tasks of its own.
- **Who may close.** A Project Assistant (`role: 'Project Assistant'`) may be invited and record a
  position under its own name; it may not write the decision file or close the meeting, which is
  refused `forbidden`.
- Tests: `core/test/meetings.test.js`.
