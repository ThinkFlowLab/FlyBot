The timeline trace no longer reports a segment as a failed write on Windows: a write is published by its rename, and the directory flush after it — which is what makes that rename survive a crash — is a POSIX call that Windows refuses on a directory handle (`EPERM` from `fsync`). The trace treated that refusal as a failed write, so a segment that was already on disk stayed "unsaved" and every newer segment was never written at all; the directory flush is now asked only where the platform has one, and a Windows trace keeps its newest segments the way a POSIX one does ([#3298](https://github.com/ThinkFlowLab/FlyBot/issues/3298)).
